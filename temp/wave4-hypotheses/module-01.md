## WH4-01-201: Import boundary accepts fabricated evidence for `ephemeral:`/anonymous soft proofs (no cryptographic evidence verification outside local context)

- Severity: HIGH | CWE: CWE-347 (Missing Verification of Cryptographic Signature) / CWE-345
- Target: src/wallet/conflict_handler.rs:~440–491 (`import_proof` Gate 4 / `VerificationOutcome::NoLocalContext` path) in interaction with src/services/conflict_manager.rs:~464–561 (`verify_proof_structure`, `gossip_soft_placeholder` branch — shape-only checks, no signature check)
- Status-Vermutung: CONFIRMED-VULN-CANDIDATE
- Threat Model: The V3 soft-proof design comment states a placeholder's "structural integrity follows from the verified layer2_signature checked at gossip ingress" — but that verification happened (if at all) only for fingerprints a wallet ITSELF admitted. At the `import_proof` boundary, Gate 3b re-verifies SST shards ONLY when `offender_id` parses as a did:key; the sibling attribution class `ephemeral:<sender_ephemeral_pub>` (the canonical offender identifier for ALL gossip soft proofs) and `anonymous` skip every cryptographic gate. Without local voucher context, Gate 4 is skipped entirely and the proof persists as a witness note. An attacker takes a victim's publicly gossiped ephemeral key `E_victim` (present in every spend fingerprint), fabricates two structurally consistent `gossip_soft_placeholder` transactions under an attacker-chosen ds_tag with garbage/never-signed shards, self-signs the reporter signature, and injects a persistent fraud record naming `ephemeral:E_victim`. The record propagates via `import_proof_from_json`/`import_proof_from_container` (same gate path) to every peer, and `check_reputation("ephemeral:E_victim")` (exact string match, queries.rs:453–478) flips to `KnownOffender` on any node that resolves counterparties via the observed linkage.
- Broken Invariant: Every offender-attributing record in the ProofStore must carry cryptographically verifiable evidence binding the claimed spender key to the embedded transactions (the anti-framing invariant of `ProofOfDoubleSpend.offender_id`). For did:key claims this is EUF-CMA via SST shards; for `ephemeral:` claims NO invariant is enforced at import — the claim's only legitimacy source (ingress signature check) is not re-established at the trust boundary that grants persistence and reputation weight.
- Fail-First-Test-Sketch: In `tests/security_audit_module_01_traps.rs`: build victim eph keypair, derive `ds_tag = H(prev_hash || E_victim)` with arbitrary prev_hash; craft `ProofOfDoubleSpend { offender_id: format!("ephemeral:{E_victim}"), fork_point_prev_hash: ds_tag, conflicting_transactions: [two gossip_soft_placeholder txs with well-formed but attacker-random trap_r/trap_s and `layer2_signature: None/garbage`], reporter_id/reporter_signature signed by ATTACKER key, proof_id = derive_proof_id(...) }`; fresh wallet WITHOUT local context → `wallet.import_proof(proof)` currently returns `Ok(())` and persists the witness note (`list_conflicts()` shows offender `ephemeral:E_victim`). Secure invariant assertion (must FAIL today): `import_proof` rejects any proof whose non-did:key `ephemeral:` claim is not backed by per-transaction `verify_fingerprint_signature`-equivalent evidence (V3 digest over embedded shards/timestamp signed by the claimed ephemeral key), or at minimum stores it without any offender linkage field intact.
- Dedupe-Check: F05/F08 cover did:key claims only (creation + import); F04/W4 discuss structural strictness of gates, not missing evidence-authenticity for the ephemeral lane; F11 covers gossip ingress bucket keys. No prior finding requires signature verification of embedded soft-proof transactions at the IMPORT boundary for non-did:key offenders.

## WH4-01-202: Genesis/init transactions accept arbitrary `trap_data` — authenticated spend-claim masquerade under attacker-chosen DS-Tags

- Severity: MEDIUM | CWE: CWE-20 (Improper Input Validation) / CWE-349
- Target: src/services/voucher_validation/chain.rs:~164 + ~310–367 (`verify_transactions` loop starts `.skip(1)`; the trap_data block incl. `validate_shard_structure` and the `ds_tag == H(prev_hash || sender_ephemeral_pub)` binding runs ONLY for non-init txs) feeding src/services/conflict_manager.rs:~77–123 (`create_fingerprint_for_transaction` trusts `trap.ds_tag` blindly whenever `trap_data.is_some()`)
- Status-Vermutung: CONFIRMED-VULN-CANDIDATE
- Threat Model: Any voucher author (issuer role — no elevated trust needed, cf. F12's custom-standard precedent) embeds `TrapData { ds_tag: D_attacker, trap_r/trap_s: cryptographically WELL-FORMED shard pair }` into the INIT transaction. L1 chain validation never inspects init trap content: `verify_transaction_integrity_and_signature` even binds the arbitrary strings VERBATIM into the V3 digest (challenge tag = t_id for init), so the crafted voucher passes reception fully. Its fingerprint is classified SPEND-typed (`is_init_fingerprint` = false because shards ≠ "none"), inherits raw transaction-level `deletable_at`, survives gossip export/ingress (validly signed by the attacker's genesis key under challenge D_attacker), and — minted twice with distinct t_ids — forms coherent single-tag buckets on every peer lacking local context for D_attacker: persistent junk "verifiable conflicts", soft-proof creation, UI/event pollution, and permanent foreign-store occupancy. Additionally the SST detection pipeline now carries shards that were never produced by the generation contract of an actual input spend.
- Broken Invariant: DS-Tag invariant completeness — `ds_tag` must be bound to real input data (`H(prev_hash || sender_ephemeral_pub)`) for EVERY fingerprint classified as a spend claim; equivalently, genesis fingerprints must be structurally incapable of carrying spend-asserting trap components. The skip(1) scoping leaves the init row outside both the shard-structure firewall (SA04-09) and the ds_tag context-binding check (replay guard).
- Fail-First-Test-Sketch: Craft a minimal valid custom-standard voucher whose init tx carries `trap_data` with `ds_tag = random_b58_32()` and a genuine `generate_sst_trap()` shard pair (attacker throwaway key). Assert SOLL: `verify_transactions` rejects trap-bearing init transactions OR `create_fingerprint_for_transaction` classifies the resulting fingerprint as init/no-trap (`is_init_fingerprint == true`) so it cannot enter gossip/detection. Actual (FAIL): chain validation returns Ok, fingerprint is spend-typed with attacker-chosen ds_tag and passes `verify_fingerprint_signature`.
- Dedupe-Check: HMSEC-SA06-11/VOID marker and WH3-00-902 address EMPTY/"none"-shard spends of NON-init transactions; SA04-09 addresses malformed shards on spends; F09 degenerate forks. No prior finding covers trap-bearing INIT transactions or the missing ds_tag input-binding on the genesis row.

## WH4-01-203: Unbounded foreign fingerprint buckets → quadratic SST extraction work and unbounded authenticated junk storage

- Severity: MEDIUM | CWE: CWE-770 (Allocation of Resources Without Limits) / CWE-407 (Inefficient Algorithmic Complexity)
- Target: src/services/conflict_manager.rs:~786–830 (`import_foreign_fingerprints` — no per-bucket/global admission cap) and src/wallet/conflict_handler.rs:~808–854 (`verify_and_create_proof` O(n²) pairwise `extract_sst_identity`) + conflict_manager.rs:~324–384 (`check_for_double_spend` materializes full buckets)
- Status-Vermutung: CONFIRMED-VULN-CANDIDATE
- Threat Model: Fingerprints are self-authenticating by design, and for ds_tags WITHOUT local input context the SA04-10 storage-time gate admits anything the attacker signs with their own keys (`None => true`). Nothing caps entries per bucket or total foreign store size at ingress (outbound is capped at MAX_FINGERPRINTS_TO_SEND=150; inbound has no symmetric limit). An attacker gossips N=5–50k validly signed fingerprints sharing one attacker-chosen ds_tag with distinct t_ids and random Base58 shard strings. Each receiving wallet (a) stores all of them for the uniform 180-day retention, (b) classifies a verifiable_conflict on EVERY `check_for_double_spend`, and (c) on conflict handling runs up to N²/2 shard-pair parse attempts (Base58 decode + point decompress + canonical scalar parse each) inside synchronous wallet code — multi-minute main-thread stalls per conflict scan, repeatable indefinitely, plus memory growth. This converts the cheap authenticated-gossip channel into a persistent CPU/memory amplification DoS against offline-first devices.
- Broken Invariant: Resource-bounded adversarial ingestion — every network-admissible evidence collection must have a bounded footprint and bounded downstream analysis cost (cf. bounded VIP/export design elsewhere). Unauthenticated-rumor eras had natural caps via distrust; the V3 signature gate made junk *authentic* and therefore unlimited.
- Fail-First-Test-Sketch: Integration test: fresh wallet, `import_foreign_fingerprints` with 2 000 hand-signed fingerprints under one ds_tag (distinct t_ids, valid-format-but-unrelated shards); assert SOLL: an admission cap/bucket bound exists (import count bounded OR conflict classification ignores oversized buckets OR extraction cost is linear/capped). Actual (FAIL): all 2 000 stored (`foreign_fingerprints[tag].len() == 2000`), `check_for_double_spend()` reports a 2 000-member verifiable conflict, and `verify_and_create_proof` performs ~2·10⁶ pair attempts (assert wall-time or instrumented pair counter below threshold).
- Dedupe-Check: F13/F16 concern n≥3 shard CONSISTENCY/attribution determinism, not bucket-size bounds or complexity; F11 concerns bucket identity, not volume. No prior finding addresses ingress volumetrics.

## WH4-01-204: `import_proof` FullyVerified write phase bypasses the AUDIT-01-F15 monotonic status guard (L2 adjudication circumvention)

- Severity: MEDIUM | CWE: CWE-285 (Improper Authorization) | Status: **KNOWN-OPEN-DEEPDIVE**
- Target: src/wallet/conflict_handler.rs:~511–548 (status writes guarded only by `VerificationOutcome::FullyVerified && winner_id`, NO prior-status match) — compare the fixed race writer at src/wallet/conflict_handler.rs:~1440–1453
- Status-Vermutung: KNOWN-OPEN-DEEPDIVE (explicitly left as-is and noted in the cumulative report §F15: "the import_proof FullyVerified path also writes status without a prior-status guard"; this deepening derives the concrete escalation)
- Threat Model: The F15 remediation made heuristic races monotonically safe, deliberately deferring to proof-import as the "strictly stronger evidence class". Deepening shows the asymmetry is exploitable in the opposite direction than assumed: the imported proof's winner is chosen purely by earliest `t_time` among its OWN conflicting_transactions after only local-context integrity checks — the winner branch is force-set to `VoucherStatus::Active` even when that very instance was previously quarantined by a SIGNED L2 verdict (`process_l2_verdict` → TriggerQuarantine) or held as Endorsed escrow... Endorsed is terminal-guarded nowhere here either (only Quarantined/Active logic exists; `_ => false` exists solely in the race writer, not here). A double-spender who controls both forks can therefore launder an adjudicated quarantine back to Active by importing a fully-verifiable variant of the same collision (their own genuinely signed transactions) with the favorable branch dated earliest — no new cryptographic *adjudication* evidence required, defeating exactly the verdict-finality F15 established.
- Broken Invariant: Status-transition monotonicity (F15): adjudicated/quarantined states may only be mutated by strictly stronger NEW cryptographic evidence; a timestamp-derived winner selection over self-controlled transactions is heuristic-class evidence and must not resurrect them.
- Fail-First-Test-Sketch: Setup: wallet holds voucher instance V containing t_id X; set `Quarantined` via the L2 verdict path (signed server envelope). Build/import a structurally genuine proof of a double spend at V's input where X is the earliest-t_time member and both conflicting txs pass `verify_transaction_integrity_and_signature` (attacker-owned honest signatures). Assert SOLL (mirroring f15 semantics): pre-existing Quarantined/adjudicated status is NOT overwritten to Active by the import write phase. Actual (FAIL): `instance.status == Active` after `import_proof`.
- Dedupe-Check: Documented observation of F15 (not a new discovery class), deepened here into a concrete adjudication-circumvention scenario per the KNOWN-OPEN marking rule; NOT counted as a novel vulnerability candidate.
