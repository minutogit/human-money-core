## Hypotheses

### HYP-02-1: Issuance Firewall Bypass via SAI Alias (string identity comparison instead of raw-key comparison)
- Severity: MEDIUM
- CWE: CWE-290 (Authentication Bypass by Alternate Name)
- Target: src/services/voucher_manager/balance.rs:33-48 (flaw at :37; correct pattern at :44-48); enforcement call site src/services/voucher_manager/transaction.rs:50; contrast src/services/voucher_validation/signatures.rs:69-96
- Attack:
  1. Creator holds seed S and maintains two profiles (explicitly supported workflow — cf. device-handover guidance in app_service/seal_handler.rs:445-456, "OPTION B"): profile A with root ID `did:key:zK` and profile B with alias ID `shop:c1@did:key:zK`. Both resolve to the identical public key K.
  2. Profile A issues a voucher; `voucher.creator_profile.id = "did:key:zK"`. Standard defines `issuance_minimum_validity_duration = "P1Y"` (circulation firewall protecting third-party recipients from near-expiry vouchers).
  3. Months pass; remaining validity < P1Y. Profile A transfers the voucher to profile B (same key ⇒ firewall's own self-transfer exception, correctly key-compared at balance.rs:47, permits this).
  4. Profile B spends to a third party: wallet passes its own `identity.user_id` as `sender_id` (wallet/transaction_handler.rs:863-869), i.e. `"shop:c1@did:key:zK"`.
  5. `validate_issuance_firewall` step 2 executes `if sender_id != creator_id { return Ok(()) }` — a STRING comparison. Alias ≠ root string ⇒ early return before the validity time check (balance.rs:52-79). Near-expiry voucher is offloaded to an unsuspecting third party — precisely the harm the immutable standard rule exists to prevent. Chain validation never rejects this: non-init senders are not constrained to any identity relationship with the creator.
- Root cause: Inconsistent identity equivalence semantics. Everywhere else the codebase treats identities of one key as interchangeable via raw 32-byte comparison (signatures.rs:82 creator attribution; signatures.rs:91 duplicate-signer firewall; balance.rs:44-48 self-transfer exception in the *same function*), but the firewall's creator-detection gate compares opaque user-ID strings, which the SAI/prefix system explicitly permits to differ per profile.
- Confidence: HIGH (logic fully traced end-to-end; exploit requires only the supported multi-profile-per-seed workflow)
- Testable: YES — integration test: build a standard with `issuance_minimum_validity_duration = "P1Y"`; create voucher with creator ID = root DID of key K; craft `valid_until` ≈ now + 2 months (>0, < min duration); call `crate::services::voucher_manager::validate_issuance_firewall(&voucher, &standard, "<alias>:x@<same did:key>", "<third party did>")`. Secure invariant asserted: MUST return `Err(InvalidValidityDuration …)` (firewall recognizes the alias as the creator via `get_pubkey_from_user_id` comparison). On current code it returns `Ok(())` ⇒ test FAILS (fail-first proven).

### HYP-02-2: Fork Detection Silently Disabled for Unequal-Length Forks (compare_seals trusts nonce ordering without chain evidence)
- Severity: MEDIUM
- CWE: CWE-354 (Improper Validation of Integrity Check Value)
- Target: src/services/seal_manager.rs:259-290 (heuristic branches :271-274 and :282-284); contract violated: src/models/seal.rs:97-109 (`ForkDetected` = "hash chains do not match … **Triggers a hard lock!**"); consumer: src/app_service/seal_handler.rs:320-379 (hard lock only on `ForkDetected`)
- Attack:
  1. Adversary clones a victim wallet (seed + storage container ⇒ same signing key, same `instance_id`, so `verify_seal_integrity` passes clone/device checks, seal_manager.rs:127-138).
  2. Both devices continue from common ancestor seal N. Victim advances chain A to nonce N+k; clone fabricates chain B (each hop honestly signed, `update_seal`) up to nonce N+m with **m ≥ k+2**.
  3. Victim's app syncs against the server holding the clone-uploaded seal: `compare_remote_seal` → `verify_seal_integrity(remote)` passes (genuinely signed, matching instance/user) → `compare_seals(local N+k/A, remote N+m/B)`: same epoch, `remote.tx_nonce > local.tx_nonce + 1` ⇒ seal_manager.rs:282-284 returns `RemoteIsNewer` **without comparing any `prev_seal_hash`**.
  4. No `ForkDetected` ⇒ no `is_locked_due_to_fork` hard lock (seal_handler.rs:375-379). The divergent fork — the exact multi-device double-spend scenario the seal system exists to expose — is classified as a benign catch-up sync. Only distance-1 divergence is detected (:277-280, :263-266); equal-nonce divergence is detected (:286-289), so the adversary simply keeps their branch longer.
  5. Result: silent fork acceptance; victim gets no lockdown warning while double-spent outputs propagate.
- Root cause: The distance≥2 branches return `LocalIsNewer`/`RemoteIsNewer` unconditionally ("We trust nonce ordering as long as epochs are equal", comment at :269-270) although the local and remote heads provably do not chain to each other; the `ForkDetected` documentation promises a hard lock whenever "hash chains do not match, even though one side is newer". A conservative fallback (`ForkDetected` when immediate linkage cannot be demonstrated, or walking available intermediate seals) is acknowledged in-code but not implemented.
- Confidence: HIGH on the logic deviation (code and doc contradiction directly readable); exploitation preconditions: seed/storage compromise — which is the seal mechanism's stated threat model (clone protection rationale, models/seal.rs:61-64).
- Testable: YES — unit/integration test: build base seal; produce branch A via two `update_seal` calls (nonce 2), branch B via two independent `update_seal` calls (nonce 2 is detected — so use A=3 updates vs B=1 update). Assert secure invariant: `SealManager::compare_seals(&branch_a3, &branch_b1) == SealSyncState::ForkDetected` (divergent chains must always hard-lock regardless of distance). Current code returns `LocalIsNewer` (nonce 3 > 1+1, seal_manager.rs:271-274) ⇒ test FAILS on current code.

### HYP-02-3: Deterministic Test Keypair Generator Compiled and Publicly Exported in Production Builds
- Severity: LOW
- CWE: CWE-489 (Active Debug Code)
- Target: src/services/crypto_keys.rs:111-133 (ungated `pub fn generate_ed25519_keypair_for_tests`); re-export chain: src/services/crypto_utils.rs:7 (`pub use super::crypto_keys::*;`) → src/lib.rs:41 (`pub use services::crypto_utils;`)
- Attack:
  1. Unlike every other test facility (`test_utils` module gated at lib.rs:89, bypass API gated at lib.rs:77-86, release compile-bomb at lib.rs:57-60), this function has no `#[cfg(any(test, feature = "test-utils"))]` gate and is part of the stable public API surface of release/FFI/WASM builds.
  2. A downstream consumer (Tauri wrapper, FFI binding, example code) can construct identities via `generate_ed25519_keypair_for_tests(Some("alice"))`. The deterministic path is plain `SHA512(string)[..32]` (crypto_keys.rs:112-122) — trivially enumerable keyspace.
  3. Any wallet/voucher created with such an identity holds no real security (attacker regenerates the private key from the name), and the misuse is invisible — no panic, no warning beyond a doc-comment.
- Root cause: Test helper escaped the crate's own feature-gating convention; the AGENTS.md invariant ("test-utils feature must NEVER be enabled in release") is enforced for the bypass switch but not for weak key material generation.
- Confidence: HIGH (export path verified through lib.rs)
- Testable: NO — not provable by a runtime fail-first test (visibility/compile-surface issue). Verification is mechanical: gate the fn behind `#[cfg(any(test, feature = "test-utils"))]` (all 31 current call sites are in `#[cfg(test)]` modules or the gated `test_utils` module) and assert `cargo build --release` fails on any residual external reference. Optionally add a nightly API-surface snapshot test.

### HYP-02-4: Password-Wrapped Containers Use Below-Guidance PBKDF2 Iteration Count
- Severity: LOW
- CWE: CWE-916 (Use of Password Hash With Insufficient Computational Effort)
- Target: src/services/crypto_symmetric.rs:214-227 (`encrypt_symmetric_password`, `PBKDF2_ROUNDS = 100_000`) and :252-265 (decrypt mirror); consumers: src/services/secure_container_manager.rs:177-198 (ContainerConfig::Password wraps full TransactionBundle payloads), src/archive/file_archive.rs:193
- Attack:
  1. Container exchange with `ContainerConfig::Password` encrypts complete voucher bundles (balances, DIDs in chain, profiles) under a user-chosen password/PIN using PBKDF2-HMAC-SHA512 with 100,000 iterations and a random 16-byte salt.
  2. An adversary who captures one exchanged container performs offline guessing. OWASP 2023 password-storage guidance recommends ≥210,000 iterations for PBKDF2-HMAC-SHA512; 100k roughly halves attacker cost per guess, and typical short PINs fall to commodity GPU rigs.
  3. Decrypted bundle exposes the full transaction graph of the exported vouchers (privacy breach; no direct key compromise since master keys are not in the payload).
- Root cause: Iteration constant frozen at a 2021-era value with no policy hook; contrast Argon2id used for storage keys (crypto_utils.rs:80-100) — the weaker KDF is applied exactly where secrets leave the device.
- Confidence: MEDIUM (parameter-strength judgment; no broken invariant — flagged for DESIGN_INTENT_TRIAGE, may be an accepted mobile/WASM latency budget like the Argon2 tuning)
- Testable: YES (weak form) — a test cannot prove "too few rounds" semantically, but can pin the invariant: derive via `encrypt_symmetric_password` in a release-profile test harness and assert the derived key matches PBKDF2-HMAC-SHA512 with ≥210,000 iterations recomputed locally; fails today (100k). Alternatively assert a wall-clock lower bound per encryption under `#[cfg(not(any(test, feature = "test-utils")))]`.

## Gaps

**Instructions that produced NO finding (verified clean):**
- *Signature malleability* (checkpoint 1): No reproducible malleability. dalek-v2 canonical-scalar verification plus the codebase's own canonical-encoding gates close s±L, non-canonical scalar, and non-canonical point encodings. Base58/base64url codecs are canonical round-trips.
- *Payload completeness* (checkpoint 2): Every structural field is either inside the t_id preimage or inside the length-prefixed HMC_TX_AUTH_V3 digest (incl. deletable_at, encrypted timestamp, privacy-guard commitment, layer2_voucher_id). Voucher-level metadata anchored by voucher_hash. Detached signatures and WalletSeal payloads hash full canonical JSON minus only the crypto fields being computed.
- *HKDF/nonce handling* (checkpoints 4, 6): Random-nonce discipline uniform; HKDF usages domain-separated; DH outcomes contributory-checked on every path; did:key ingestion rejects non-prime-order points (crypto_identity.rs:265-280).
- *Preimage exposure* (checkpoint 7): Recipient/change anchors are hash commitments only; sender ephemeral reveal coincides with spend authorization by protocol design (documented SST trade-off, trap_manager.rs:25-35).

**Uncertain / observations (no formal hypothesis):**
1. **Identity-parser desync surface (UNCERTAIN):** `get_prefix_from_user_id` (crypto_identity.rs:20-35) neither sanitizes whitespace nor rejects multiple `'@'` (rfind-based), while `validate_user_id`/`get_pubkey_from_user_id` sanitize aggressively and the strict grammar gate at signatures.rs:49 blocks lenient aliases from signed containers. Residual exposure requires a user-ID string with internal whitespace/multi-@ reaching prefix extraction (change-seed info string, firewall inputs) — all current producers are locally generated via `create_user_id`, so no exploit path was found; noted as defense-in-depth debt.
2. **Dead validation of `target_prefix`** (wallet/transaction_handler.rs:432-436): the check result is discarded (comment: "we log it"). Not a security control (ownership is enforced cryptographically via anchor hash + guard decryption), but the field is advertised "for validation"; also `target_prefix` extraction for root-DID recipients yields the bogus literal `"did"` (voucher_manager/transaction.rs:249-253). Informational.
3. **`encrypt_transaction_timestamp` is XOR with a publicly derivable key** (conflict_manager.rs:905-936): provides zero confidentiality against anyone holding the public chain data; doc-comment declares this intentional (commitment/binding purpose only). Classified [likely INTENTIONAL DESIGN REQUIREMENT] per triage rule — recommend documenting the invariant in code (it is already signature-bound, so no swap risk).
4. **`check_integrity` edge case** (app_service/seal_handler.rs:51-53): `(Some(_), None)` (integrity record present, seal absent) reports `IntegrityReport::Valid` with a "// Should not happen" comment; a missing-seal state would merit an explicit report variant rather than Valid. Local-tamper-only impact.
5. **Memory hygiene nits:** `SessionCache.session_key` ([u8;32], app_service/mod.rs:98) and the `Vec<u8>` file key returned by `get_file_key` (storage/file_storage.rs:1570-1601) lack zeroize-on-drop; low practical impact, inconsistent with the otherwise strict zeroize discipline.

**Why uncertain items stayed hypotheses-out:** each lacks either an attacker-reachable path with current callers (item 1), security relevance (items 2, 3), or more than cosmetic impact (items 4, 5). They are recorded here so a future wave can re-examine them if caller patterns change.
