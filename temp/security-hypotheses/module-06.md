## H-06-1 — JWS-Header-Allowlist-Lücke: `cty` ungepinnt, unbekannte Header-Member still akzeptiert
- **Vermutung:** Der Verifier in `verify_and_import_jws_profile` pinnt nach dem SA06-06-Fix zwar `alg` und `typ`, aber NICHT `cty` (deklariertes Feld von `JwsHeader`, beim Export immer `"application/json"`) und akzeptiert beliebig viele UNBEKANNTE Header-Member (`serde_json` ignoriert unbekannte Felder; kein `deny_unknown_fields`). Ein Angreifer kann also mit seinem EIGENEN Schlüssel ein syntaktisch gültiges Profil-JWS mit `cty: "application/trust-assertion+json"` oder injizierten Extension-Membern (`jku`, `jwk`, Custom-Flags) signieren, das die Verifikation passiert. Solange nur PublicProfile verifiziert wird, ist der Impact begrenzt; sobald derselbe Parser/Verifier weitere Artefaktklassen guardt (TrustAssertion ist als Container-Payload bereits routingfähig, siehe H-06-2), wird Header-Verwechslung zur Cross-Type-Injection. Das ist genau die „fehlende Header-Checks über alle Profile hinweg“-Lücke, die SA06-06 nicht geschlossen hat.
- **Betroffene Invariante:** Strikte Envelope-Validierung vor Payload-Processing (Audit-Invariante 3); RFC 7515 Absender-Intent (`cty`) muss dem erwarteten Artefakt entsprechen.
- **Zielcode:** `src/services/jws_profile_service.rs` :: `verify_and_import_jws_profile` (~Zeilen 99–119; Header-Struct `JwsHeader` Zeilen 16–24 ohne `deny_unknown_fields`)
- **Geplanter Fail-First-Test:** Attacker-signiertes Profil-JWS mit manipuliertem Header bauen (`alg: "EdDSA"`, `typ: "JWT"`, aber `cty: "application/trust-assertion+json"` plus unbekanntem Member `"jku": "https://attacker.example/x.jwk"`), korrekt mit Angreifer-Key über `header.payload` signieren, dann:
  `assert!(verify_and_import_jws_profile(&attack_jws).is_err(), "JWS with unpinned cty / unknown header members must be rejected");`
  Schlägt auf unpatched Code FEHL (Import succeeds), weil nur `alg`/`typ` geprüft werden.
- **Triage-Vorabcheck:** Könnte `[INTENTIONAL DESIGN REQUIREMENT]` sein? Nein — Liberalität beim `cty`/Unknown-Member bringt keinen Interop-Gewinn (die Library emittiert selbst immer exakt `{alg, cty, typ}`); eine Allowlist schadet legitimen Clients nicht. Kein 4-Fragen-Anhaltspunkt für Design-Absicht.
- **Priorität:** MEDIUM

## H-06-2 — Trust-Assertion-Forgery: Signatur deckt nur `assertion_id`, nicht `trust_level`/`context`; keine Verifier-Instanz vorhanden
- **Status Phase B:** CONFIRMED-PENDING — manuelle Verifikation bestätigt Spec-Fluch (`issuer_signature` bindet nur `assertion_id = hash(issuer+subject+timestamp)`; `trust_level`/`context` ungeschützt); da KEIN Verifier in src/ existiert (nur routbares `PayloadType::TrustAssertion`) gibt es keinen minimalen Fix-TARGET im Code → Conformance-Harness `sa06_07_trust_assertion_signature_must_bind_all_semantic_fields` als `#[ignore = "HMSEC-SA06-07 pending architectural fix"]` angelegt (dokumentiert Soll-Invariante + Exploit-Nachweis); Protokoll-Fix VOR jeder Implementierung zwingend; Finding HMSEC-SA06-07.
- **Vermutung:** Die Spezifikation `protocols/trust/1.0/assertion.md` definiert `issuer_signature` als Signatur des Issuers ÜBER DIE `assertion_id` ALLEIN, wobei `assertion_id = hash(issuer_id + subject_id + timestamp)` deterministisch ist. Konsequenz: (a) `trust_level` und `context` sind KRYPTOGRAFISCH UNGESCHÜTZT — jeder, der EINE legitime Assertion gesehen hat, kann `trust_level` (z. B. `"direct"` → `"endorsement"`) und `context` beliebig umschreiben, ohne dass eine zukünftige, spec-konforme Verifikation dies je bemerkt; (b) fehlende Nonce/Expiry + deterministische ID ermöglichen Replay identischer Assertions über Kanäle hinweg; (c) im Code existiert KEINE Verifikationslogik (Grep: keine `verify_trust_assertion`-artige Funktion), obwohl `PayloadType::TrustAssertion` (`src/models/secure_container.rs:23`) bereits als Container-Payload-Typ routingfähig ist — d. h. die erste naive Implementierung nach Spec würde gefälschte Assertions durchwinken. Trust-Assertions sind das WoT-Fundament für Bürgen/Notare → Forgery untergräbt die gesamte Vertrauenskette.
- **Betroffene Invariante:** Protokoll-Envelope-Validierung vor Payload-Processing; Integrität der Vertrauensbekundung (Signatur muss ALLE semantisch relevanten Felder binden — analog PRIVACY_MATRIX-Konsequenzdenken).
- **Zielcode:** `protocols/trust/1.0/assertion.md` :: Schema-Definition (Zeilen 13–19, insb. `assertion_id`- und `issuer_signature`-Definition); `src/models/secure_container.rs` :: `PayloadType::TrustAssertion` (Zeile 23) + fehlender Receive-/Verify-Pfad
- **Geplanter Fail-First-Test:** Spec-konforme Trust-Assertion konstruieren (Issuer signiert `assertion_id` korrekt mit eigenem Key), dann `trust_level` und `context` mutieren und asserten:
  `assert!(verify_trust_assertion(&tampered_assertion).is_err(), "Trust assertion with swapped trust_level/context must fail verification");`
  Hinweis für Phase B: Da noch kein Verifier existiert, wird der Test als Conformance-Harness gegen den zu implementierenden Verifier (`services/trust_*` bzw. JWS-basiert) angelegt; auf unpatched/naivem Code (Spec-getreue Prüfung nur über `assertion_id`) MUSS das Assert fehlschlagen. Bis zur Existenz eines Stubs ist der Test auszufalten/skip-markiert zu dokumentieren.
- **Triage-Vorabcheck:** Könnte `[INTENTIONAL DESIGN REQUIREMENT]` sein? Die ID-vor-Signatur-Bindung könnte als „kleine, stabile Signaturbasis“ intendiert sein — aber der 4-Fragen-Check fällt negativ aus: Es gibt keinen funktionalen Grund, `trust_level`/`context` außerhalb der Signatur zu lassen (Assertion ist winzig, kanonisches JSON der Gesamtstruktur kostet nichts). Spec-Fix VOR Implementierung ist billig; danach teuer.
- **Priorität:** HIGH

## H-06-3 — Metadata-Minimization: unblinded ISO-8601-Erstellungszeit wird in Private-Mode-Bundles fest in `bundle_id`-Commitment eingebrannt
- **Vermutung:** `create_and_encrypt_bundle` setzt `timestamp: get_current_timestamp()` UNBEDINGT und auf Sekundengenauigkeit (RFC 3339) — auch wenn die Transferkette vollständig anonym (Private Mode) ist. Da `bundle_id = hash(canonical(bundle))` den Timestamp einschließt und `sender_signature` die `bundle_id` signiert, ist die exakte Erstellzeit kryptografisch COMMITTED: Nachträgliches Blinding/Coarsening (z. B. auf Tagesgenauigkeit) ist nachträglich unmöglich, ohne Signatur und ID-Kette zu brechen. Empfänger und jeder spätere Inhaber des entschlüsselten Bundles (Backup-Leak, Weiterleitung, Dispute-Export) erhält das exakte Sendezeitfenster des „anonymen“ Transfers. IP-Hints sind im Core (Offline-First, keine Netzwerk-Calls) nicht relevant; Kontostände liegen nur lokal in Events — der offene Vektor „unblinded Timestamps“ ist damit der konkrete Restbefund. Beleg dafür, dass der Timestamp KEINE Sicherheitsfunktion hat: Empfangsseitige Zeitvalidierung nutzt ausschließlich `last_tx.t_time` (`process_encrypted_transaction_bundle`, Hard-Reject far-future), `bundle.timestamp` wird lediglich in `TransactionBundleHeader` kopiert (`models/profile.rs:124`) und sonst nie konsumiert.
- **Betroffene Invariante:** Metadata-Minimization (Audit-Invariante 2): „Transferred bundles must not leak extraneous metadata (e.g. … unblinded timestamps …)“.
- **Zielcode:** `src/services/bundle_processor.rs` :: `create_and_encrypt_bundle` (Zeile 47: `timestamp: get_current_timestamp()`; Commitment via Zeilen 55–58)
- **Geplanter Fail-First-Test:** Private-Mode-Transfer (wie SA06-01-Fixture, `use_privacy_mode = Some(true)`), Bundle entschlüsseln und asserten, dass die Metadaten-Zeit geblendet/coarsened ist (Soll: Tagesgranularität oder neutraler Marker):
  ```rust
  let ts = chrono::DateTime::parse_from_rfc3339(&decrypted_bundle.timestamp).unwrap();
  assert_eq!(ts.time(), chrono::NaTime::MIDNIGHT /* bzw. Blinding-Marker */,
      "HMSEC: private-mode bundle must not commit an exact creation timestamp into bundle_id");
  ```
  Schlägt auf unpatched Code FEHL (exakte Sekundenzeit committed). Alternativ-Invariante falls Fix andersrum erfolgt: `is_anonymous_bundle(&bundle)` ⟹ `timestamp` ist kein parsebarer RFC-3339-Wert mit Sub-Day-Präzision.
- **Triage-Vorabcheck:** Könnte `[INTENTIONAL DESIGN REQUIREMENT]` sein? Fraglich — Argumente DAFÜR wären Dispute-Forensik (aber die läuft laut SA06-05-Design über lokale Event-Logs und `t_time` der Transaktionskette, nicht über `bundle.timestamp`) oder Replay-Dedupe (läuft über `bundle_id`/Fingerprints). Da NIEMALS Sicherheitslogik den Timestamp konsumiert, spricht alles für Legacy-Restmetadaten → kein Design-Requirement erkennbar.
- **Priorität:** MEDIUM

## H-06-4 — Envelope-Signatur-Privacy-Gate umgehbar: gemischte Multi-Standard-Bundles reaktivieren die Permanent-Key De-Anonymisierungs-Oracle (SA06-01-Variante)
- **Status Phase B:** CONFIRMED+FIXED — Fail-First-Test `sa06_08_mixed_visibility_bundle_must_not_carry_permanent_key_envelope_signature` FAIL auf unpatched (Public+Stealth-Multi-Source-Transfer, use_privacy_mode=None → Envelope-Signatur vorhanden & gegen Alice-Key verifizierbar); WICHTIG: Trigger braucht Public-Standard (real-DID-Empfänger), nicht Flexible (dessen „öffentlich“-Kette hat anonymen Empfänger und zählt via zweitem Disjunkt schon als anonym); Triage `[CONFIRMED VULNERABILITY]` (4-Fragen: Transport-Boundary ja / Forensik unberührt / SA06-01-Konsens dagegen / Public-only-Bundles behalten Signatur); Fix: `is_anonymous_bundle` ALL→ANY (`bundle_contains_anonymous_chain`, bundle_processor.rs) — Modul-Filter 7 grün; Finding HMSEC-SA06-08.
- **Vermutung:** Der SA06-01-Fix entfernt die Permanent-Key-Envelope-Signatur NUR wenn `is_anonymous_bundle()` true liefert — und das Gate ist ALL-OR-NOTHING pro Container: JEDE Voucher-Kette im Bundle muss als letzte Transaktion anonym sein (`sender_id.is_none() || recipient == ANONYMOUS_ID`, `bundle_processor.rs:90–97`). Ein einziger nicht-anonymer Chain-Abschnitt genügt, damit `container.signature` mit dem PERMANENTEN Identity-Key über `i` signiert bleibt — öffentlich verifizierbar gegen einen Candidate-Key-Pool, und zwar für den GESAMTEN Container inklusive aller privaten Unterketten. Realistischer Trigger ohne jeden Regelbruch: `MultiTransferRequest` mit mehreren Quellen ÜBER VERSCHIEDENE Standards bei `use_privacy_mode = None` — dann entscheidet das jeweilige Standard-Feature `privacy_mode` pro Voucher (`PrivacyMode::Public` neben `PrivacyMode::Private` im selben Request/Bundle), das Gate kippt auf „nicht anonym“, und der Absender de-anonymisiert sich selbst (und alle Mitgelieferten) per Ed25519-Test auf `verify(P, i, sig)` — exakt die SA06-01-Oracle-Situation, nur über einen anderen, legitim aussehenden Pfad. Das bestehende SA06-01-Testfixture deckt diesen Mixed-Case NICHT (einzelner Standard, reiner Private-Transfer).
- **Betroffene Invariante:** Private Mode OHNE Permanent-Key-Signatur im Transfer-Envelope (Kern-Invariante Modul 06 / PRIVACY_MATRIX `sender_sig`: Private ⟹ MUST NOT be present).
- **Zielcode:** `src/services/bundle_processor.rs` :: `is_anonymous_bundle` (Zeilen 77–97, insb. `all()`-Gate) und `create_and_encrypt_bundle` (Zeilen 69–79)
- **Geplanter Fail-First-Test:** Wallet mit ZWEI Vouchern unter zwei Standards (einer mit `privacy_mode = Public/Flexible`, einer `Private`), kombinierter Transfer an Bob mit `use_privacy_mode = None`; Container parsen und:
  ```rust
  let sig_bytes = bs58_decode_helper(&container.signature);
  let sig = Signature::from_slice(&sig_bytes).unwrap();
  assert!(
      !verify_ed25519(&alice.public_key, container.i.as_bytes(), &sig),
      "Mixed-visibility bundle must not carry a permanent-key envelope signature \
       that de-anonymizes the private sub-chain (SA06-01 oracle regression)"
  );
  ```
  Zusätzlich Soll-Invariante: Bob muss das Bundle weiterhin fehlerfrei processen können. Schlägt auf unpatched Code FEHL (Signatur vorhanden und verifizierbar).
- **Triage-Vorabcheck:** Könnte `[INTENTIONAL DESIGN REQUIREMENT]` sein? Denkbar wäre das Argument „öffentliche Ketten verdienen Envelope-Authentizität“ — aber der Fix von SA06-01 zeigt den gegenteiligen Konsens: Innere Bundle-Signatur ist IMMER ausreichend (`open_and_verify_bundle` Zeilen 157–166 behandelt leere Signatur als legitimen Fall). Ein Per-Container-Gate statt All-or-Nothing (bzw. Gate auf deklarierter `privacy_mode` statt geratener Chain-Form) bricht keine dokumentierte Funktion.
- **Priorität:** HIGH

## H-06-5 — Wrapper-Spoofing-Fix-Asymmetrie: Signing-Workflow-Pfade prüfen weder `i`-Rebinding noch Envelope-Signatur
- **Status Phase B:** CONFIRMED+FIXED — Fail-First-Test `sa06_09_signing_paths_must_rebind_container_integrity_id` FAIL auf unpatched (Teil A: gestohlenes (i,signature) auf fremdem VoucherForSigning-Container wird von open_voucher_signing_request akzeptiert; Teil B: Graft auf DetachedSignature + `unprotected`-Metadaten-Injektion wird von process_and_attach_signature akzeptiert); Triage `[CONFIRMED VULNERABILITY]` (Cleartext-Preview-Intent betrifft nur Signaturenforcement, nicht i-Bindung; ehrliche Erzeuger erfüllen Invariante immer); Fix: neuer Helper `verify_container_integrity_binding` (secure_container_manager.rs), gerufen in app_signature_handler.rs (pre-decrypt) und wallet/signature_handler.rs (post-decrypt, damit AEAD-Error-Präzedenz des Bestandstests api_wallet_signature_fail_tampered_container erhalten bleibt); Signatur-Enforcement bewusst NICHT nachgerüstet (Attribution, nicht Integrität; Produktentscheid nötig) — Modul-Filter 8 grün + api_wallet_signature-Regression 6 grün; Finding HMSEC-SA06-09.
- **Vermutung:** Der SA06-02-Fix (Recompute von `container.i` und `bundle_id` vor jeder weiteren Verarbeitung) wurde AUSSCHLIESSLICH in `open_and_verify_bundle` implementiert. Die beiden anderen Receive-Pfade des Protokoll-Sets akzeptieren Container ohne jede Integritäts-Rebindung: (a) `AppService::open_voucher_signing_request` deserialisiert, prüft nur `c == VoucherForSigning` und öffnet direkt; (b) `Wallet::process_and_attach_signature` (DetachedSignature-Empfang) prüft nur `c == DetachedSignature`. Folgen: (1) Gestohlene `(i, signature)`-Paare (SA06-02-Stil) lassen sich auf manipulierte VoucherForSigning/DetachedSignature-Container ummontieren, OHNE dass der Empfängerpfad es erkennen KÖNNTE; (2) alle AEAD-exempten Envelope-Felder — `unprotected` (explizit „not encrypted or signed“), `salt`, `et`, `c` — sind auf diesen Pfaden frei manipulierbar: `c`-Flip steuert die Routing-Entscheidung in `process_and_attach_signature`/`process_encrypted_transaction_bundle` (Zeilen 495–501 in transaction_handler.rs), `unprotected` transportiert beliebige, unverifizierte Metadaten bis in Host-/UI-Schichten. Aktuelle Exploit-Tiefe ist durch AEAD-Bindung von Ciphertext+Protected-Header begrenzt (Decryption schlägt bei Content-Manipulation fehl), aber das ist reine Defense-in-Depths-Restsubstanz — dieselbe Angriffsklasse, die SA06-02 als CRITICAL eingestuft hat, lebt auf diesen Pfaden fort.
- **Betroffene Invariante:** Strikte Envelope-Validierung vor Payload-Processing; Wrapper-vs-Payload-Bindung (`i` = hash(Content)) muss auf ALLEN Protokollpfaden gelten, nicht nur im Transfer-Pfad.
- **Zielcode:** `src/app_service/app_signature_handler.rs` :: `open_voucher_signing_request` (Zeilen 46–73, insb. fehlender i-Recompute vor Zeile 66); `src/wallet/signature_handler.rs` :: `process_and_attach_signature` (Zeilen 146–158, fehlender i-Recompute/Signaturprüfung vor `open_secure_container`)
- **Geplanter Fail-First-Test:** Legitimes verschlüsseltes Signing-Request von Alice an Guarantor erzeugen; `(i, signature)` stehlen und auf einen manipulierten Container mit anderem Payload/`unprotected`-Metadatum ummounten (Rezept wie SA06-02 Step 3, aber PayloadType::VoucherForSigning, Verschlüsselung an Guarantor); dann:
  ```rust
  assert!(
      app.open_voucher_signing_request(&attack_bytes, None).is_err(),
      "Signing-request path must reject containers whose content does not match their integrity id i"
  );
  ```
  Analog für DetachedSignature via `wallet.process_and_attach_signature`. Schlägt auf unpatched Code FEHL (Manipulation wird akzeptiert/geladen).
- **Triage-Vorabcheck:** Könnte `[INTENTIONAL DESIGN REQUIREMENT]` sein? Für Cleartext-Signing-Requests gilt bewusst: keine Envelope-Authentizität, Inhalt wird vom Bürgen reviewt und die resultierende Signatur bindet genau den reviewten Inhalt — dieser Teil wäre ggf. `[INTENTIONAL DESIGN REQUIREMENT]` (Preview-Charakter). Der Test ist deshalb auf VERSCHLÜSSELTE Container (Asymmetric) zu beschränken; dort gibt es keinen Preview-Begriff, der fehlendes i-Rebinding rechtfertigen würde.
- **Priorität:** HIGH

## H-06-6 — Attacker-controlled Display-Name Injection: `sender_profile_name` fließt ungeprüft in `EventBffData.counterparty_name` und persistente Bundle-Historie
- **Status Phase B:** CONFIRMED+FIXED — Fail-First-Test `sa06_10_received_display_name_must_be_sanitized_and_bounded` FAIL auf unpatched (10.005-Zeichen-Name mit U+200D/U+202E landete roh im TransferReceived-Event); Triage `[CONFIRMED VULNERABILITY]` (4-Fragen: Cross-Boundary ja / Forensik unberührt — counterparty_id-Retention SA06-05 explizit getestet-intakt / keine dokumentierte Verbatim-Pflicht / Display-Funktion bleibt); Fix: `sanitize_display_name` (Cc+Cf-Strip, 64-Zeichen-Bound) einmalig am Ingestion-Punkt in `process_encrypted_transaction_bundle_inner` direkt nach `open_and_verify_bundle` → deckt Event-Feed UND BundleMetadataStore-Historie; Legitimnamen unverändert (Regression-Guard im Test) — Modul-Filter 9 grün + event-Filter 18 grün; Finding HMSEC-SA06-10.
- **Vermutung:** Beim Empfang wird `counterparty_name: bundle.sender_profile_name.clone()` (transaktion_handler.rs:452, weitergereicht in Zeilen 459–471) ungeprüft — Länge, Steuerzeichen, Unicode-Spoofing (Homoglyphen/Typo-Squatting auf bekannte Community-Namen) — in `WalletEvent.bff_data` übernommen, via `get_event_history` an UI/Host geliefert und parallel in der persistenten `BundleMetadataStore.history` abgelegt. Ein Angreifer kann einem Opfer also Events unterschieben wie „Received from ‹Alice Support Team›“ oder ‹offizieller Standardname› (Phishing/Social Engineering direkt im vertrauenswürdigen Event-Feed), plus Ressourcen-Bloat durch unbegrenzte String-Längen in einem dauerhaft wachsenden Log (jede empfangene Mail = ein Eintrag). Das ist bewusst JENSEITS der geschützten Counterparty-DID-Retention (SA06-05 🛡️, Feld `counterparty_id`): Hier geht es um das ANGREIFER-KONTROLLIERTE Feld `counterparty_name`, das keinerlei Verifikation gegen ein Profil/JWS erfährt (im Gegensatz zu `creator_profile` im Voucher, das signierte Profile trägt).
- **Betroffene Invariante:** Metadata-Minimization/Integrität des lokalen Event-Feeds (Audit-Invariante: `WalletEvent`/`EventBffData` dürfen keine manipulierbaren, nicht-verifizierten Metadaten an UI/Host-Listener durchreichen); DoS-Resistenz des Event-Logs.
- **Zielcode:** `src/wallet/transaction_handler.rs` :: `process_encrypted_transaction_bundle` (Zeile 452: `counterparty_name: bundle.sender_profile_name.clone()`, Emit in Zeilen 458–472); Persistenz: `src/models/profile.rs` :: `TransactionBundleHeader.sender_profile_name` (Zeilen 78–79, 111–113); Modell: `src/models/wallet_event.rs` :: `EventBffData` (Zeilen 52–54)
- **Geplanter Fail-First-Test:** Angreifer-Bundle mit `sender_profile_name = Some("A".repeat(10_000) + "\u{200D}Alice\u{200E}")` an Opfer-Wallet senden; nach Verarbeitung:
  ```rust
  let ev = victim_wallet.pending_events.iter()
      .find(|e| e.event_type == WalletEventType::TransferReceived).unwrap();
  assert!(
      ev.bff_data.counterparty_name.as_ref().map_or(false, |n| n.chars().count() <= 64 && !contains_invisible_or_direction_chars(n)),
      "Unverified sender-supplied display names must be sanitized/bounded before entering the trusted event feed"
  );
  ```
  Alternativ (strikere Soll-Implementierung): `counterparty_name` darf nur aus einem VERIFIZIerten Profil (JWS-Import/Contact-Store) stammen, sonst None — Assert darauf schlägt heute ebenfalls fehl.
- **Triage-Vorabcheck:** Könnte `[INTENTIONAL DESIGN REQUIREMENT]` sein? Die Retention des NAMENS an sich ja (Display-Zweck, analog SA06-05) — aber NICHT dessen Ungeprüftheit: Sanitizing/Längenlimit/Provenance-Pflicht ändert die Forensik-Funktion nicht (die hängt an `counterparty_id`), daher ist der Vektor vom geschützten Design NICHT gedeckt.
- **Priorität:** MEDIUM

INGRESS: neue Helper `assign_local_retention_to_wire_entry` setzt auf jedem akzeptierten Fremd-Fingerprint eine uniforme lokale Deadline (`FOREIGN_FINGERPRINT_RETENTION_DAYS = 180`, RFC3339-kompatibel zur String-Vergleichs-Cleanup), angewendet in `import_foreign_fingerprints` UND `process_received_fingerprints`; Dedupe dort auf Beweis-Identität (`t_id`) umgestellt, da strukturelle Gleichheit durch die session-spezifische Deadline brechen würde. Lokale Retention-Semantik (Monatsrundung in `create_fingerprint_for_transaction`) unverändert — nur der Draht wird generalisiert; Signatur-Gate unberührt (Spend-Challenge bindet `deletable_at` nicht; Init-Einträge werden vor der Umschreibung abgewiesen).
- **Vermutung:** Für Spends setzt `create_fingerprint_for_transaction` `deletable_at` auf die mikrosekundengenaue Monat-Ende-Rundung von `voucher.valid_until`. Alle Transaktionen eines gesamten Voucher-Baums (Splits, Weiterveräußerungen, Change-Äste) teilen EXAKT denselben String, und `export_own_fingerprints` serialisiert das Feld unverändert in den Peer-Abgleich (`import_foreign_fingerprints` akzeptiert es). Ein Gossip-Beobachter cluster thus private-mode Spends über identische `deletable_at`-Werte zu Ursprungs-Voucherlinienien und erhält zusätzlich den Gültigkeitsmonat — Linkability genau der Art, die Private Mode verhindern soll (analog H-06-3, aber auf dem GOSSIP-Kanal statt im Bundle). Die Rundung schützt nur gegen Exaktzeit-Attribution, nicht gegen Mengen-/Familien-Korrelation; lokal dient das Feld als Retention-Deadline (`cleanup_*_histories` parst RFC3339) — Fix muss therefore Kanaltrennung vorsehen, nicht Streichung.
- **Betroffene Invariante:** Metadata-Minimization auf dem Transportweg (Gossip-Fingerprints sind Netzwerk-Envelopes); „Private Mode ohne verknüpfbare Metadaten“ zwischen ansonsten anonymen Spends.
- **Zielcode:** `src/services/conflict_manager.rs` :: `create_fingerprint_for_transaction` (Zeilen 29–57 Rundung, Zeilen 97–112 Zuweisung für Spends); Wire-Export `export_own_fingerprints` (Zeilen 641–647) / Ingress `import_foreign_fingerprints` (Zeilen 656–690).
- **Geplanter Fail-First-Test:** Zwei Splits desselben Vouchers privat ausgeben, Fingerprints beider Spends erzeugen und exportieren: `assert_ne!(fp_a.deletable_at, fp_b.deletable_at, "...")` ist zu schwach (gleicher Wert ist legitim bei lokaler Retention); Soll-Invariante stattdessen: Im EXPORT-Format darf `deletable_at` kein parsebarer voucher-abgeleiteter RFC3339-Zeitwert sein (neutraler Retentionsmarker oder pro-Fingerprint-Zufallswert mit äquivalenter Cleanup-Semantik) — Conformance-Assert `DateTime::parse_from_rfc3339(&fp.deletable_at).is_err()` über exportierte Fingerprints schlägt auf unpatched Code FEHL (echtes Datum enthalten).
