## H-03-1 — Lexikografischer String-Vergleich von Decimal-Beträgen (Fail-Open bei Mengen-Limits)
- **Vermutung:** Beträge sind im Voucher-/Transaktionsmodell bewusst als `String` serialisiert (`Transaction.amount: String`, `models/voucher.rs:145`; `ValueDefinition.amount: String`, `models/voucher.rs:29`). Die CEL-Engine bietet für Skalenprüfung zwar `check_decimals`, aber KEINE numerische Vergleichshilfe für Magnituden. Schreibt ein Standard-Autor ein Mengen-Limit als Ordering-Vergleich (`Transaction.amount < '9'`, `<= '5000'`), vergleicht cel-interpreter zwei `Value::String` **lexikografisch bytewise**: `"15" < "9"` → `'1' < '9'` → `true`. Ein Limit-Ausdruck wird also von Werten ERFÜLLT, die das Limit verletzen — Fail-Open in die gefährliche Richtung. Der AST-Pre-Check `eval_and_check_ast` implementiert `<`/`<=`/`>`/`>=` gar nicht (fällt in den generischen Catch-All, dynamic_policy_engine.rs:377–385, liefert `Null`) und neutralisiert sich damit selbst; die eigentliche Interpreter-Auswertung entscheidet und gibt `Ok(true)` zurück. Betroffen ist jeder Ausdruck der Form `...amount... < / <= / > / >= '<Literal>'` über PRESENT Felder (der M03-001-Kontrolltest deckt nur Ordering über FEHLENDE Felder ab, nicht String-vs-String-Semantik über vorhandene).
- **Betroffene Invariante:** Fail-Closed Principle (Audit-Invariante #2) — policy-verletzende Vouchers/Transfers dürfen nie `Ok(true)` liefern; zudem Determinismus/Integrität der Geschäftsregeln (Invariante #1), da identische Regeln auf verschiedenen Plattformen konsistent falsch sind.
- **Zielcode:** src/services/dynamic_policy_engine.rs :: DynamicPolicyEngine::evaluate_rule (~L20–65) + eval_and_check_ast Catch-All (~L377–385); Konsumer: src/services/voucher_validation/rules.rs :: get_failing_custom_rules (~L31–40)
- **Geplanter Fail-First-Test:** `assert!(!matches!(DynamicPolicyEngine::evaluate_rule("Transaction.amount < '9'", &voucher, Some(&tx_with_amount_15)), Ok(true)), "string-typed magnitude limit must not pass for violating value")` — mit `tx = {"amount": "15"}`. Auf unpatched Code liefert die Engine `Ok(true)` (lexikografisch `"15" < "9"`), das assert schlägt fehl → Lücke bewiesen. Sekundär-Assert: gleicher Ausdruck mit `"5000"` gegen Limit `'100'` muss ebenfalls nicht `Ok(true)` sein.
- **Triage-Vorabcheck:** Kaum `[INTENTIONAL DESIGN REQUIREMENT]`: Das String-Format der Beträge ist kryptographisch motiviert (AGENTS.md: Serialisierungsstabilität), aber dass Ordering-Vergleiche darüber stillschweigend lexikografisch werden, ist kein dokumentiertes Designziel. Falls das Triage-Ergebnis „Autoren-Fehler, dokumentieren“ lautet, wäre Mindestmaß ein Import-/Compile-Time-Warning oder eine Engine-Level-Ablehnung von Ordering-Vergleichen zwischen Strings mit Dezimal-Inhalt (fail-closed) plus Invariantentest.
- **Priorität:** CRITICAL
- **Status Phase B:** CONFIRMED+FIXED — Lexikografie bewiesen (`Ok(true)` für "15"<'9'), Fail-Closed-Guard für Ordering über nicht-numerische Operanden in `eval_and_check_ast` (AUDIT-M03-003), Suite 12/12 grün.

## H-03-2 — Silent Overwrite & fehlende Konflikt-Erkennung beim Standard-Import (Container-/UUID-Swap)
- **Vermutung:** `import_voucher_standard` prüft NUR die interne Selbstkonsistenz des Standards (Signatur durch den im File selbst angegebenen `issuer_id`) und schreibt dann bedingungslos `target_dir/<uuid>/standard.toml` via `fs::write` (standard_container_handler.rs:141–150). Es existiert KEIN Check, ob unter dieser UUID bereits ein Standard installiert ist. Konsequenzen: (a) **Brick/DoS:** Ein Angreifer verschickt ein `.standard`-Bundle mit identischer `immutable.identity.uuid`, aber anderem Immutable-Zone-Inhalt; beim Import überschreibt es stillschweigend die bestehende Installation → alle lokalen Vouchers, deren `voucher_standard.standard_definition_hash` auf den alten Hash bindet (identity.rs:19–25), failen fortlaufend bei jeder Validierung. (b) **Entschärfte Variante („weakened-but-hash-valid“):** Opfer importiert die entschärfte Variante, bevor es eigene Vouchers erzeugt; neue Vouchers binden an den schwächeren Hash und umgehen die ursprünglichen Regeln (z.B. gelockerte `custom_rules`/`additional_signatures_range`). (c) Zusätzlich ist `fs::write` nicht atomar (temp+rename wie in `FileStorage` üblich) — ein Crash mitten im Schreiben hinterlässt einen korrupten `standard.toml`. `delete_voucher_standard` hat Traversal-Schutz und UUID-Mismatch-Behandlung (L171–202), `import` hat keinerlei entsprechende Sorgfalt.
- **Betroffene Invariante:** Immutability & Integrity (Audit-Invariante #3): Ein Standard kann lokal ausgetauscht/überschrieben werden, ohne dass die Container-Hash-Chain dies verhindert — der Hash-Chain-Schutz bindet Vouchers an Hashes, schützt aber nicht die Installations-Integrität des Standards unter einer UUID.
- **Zielcode:** src/app_service/standard_container_handler.rs :: AppService::import_voucher_standard (~L109–153, insbesondere L144–150)
- **Geplanter Fail-First-Test:** Zwei gültige, jeweils korrekt selbst-signierte Standards A und B mit gleichem `immutable.identity.uuid`, aber unterschiedlichem `immutable.features.amount_decimal_places`. Import A → Ok; Import B → `assert!(result.is_err(), "import must refuse to silently overwrite an installed standard under the same uuid")` UND `assert_eq!(fs::read_to_string(dir/<uuid>/standard.toml), A_content)` — auf unpatched Code gibt Import B `Ok(uuid)` zurück und der File-Content ist B → beide asserts schlagen fehl.
- **Triage-Vorabcheck:** Teilaspekt könnte `[INTENTIONAL DESIGN REQUIREMENT]` sein: „Re-Import aktualisiert den Standard“ (Update-Pfad). Dann wäre das Soll-Verhalten: explizite Update-Semantik mit Konflikt-Detection (Hash-Vergleich alt/neu, Unterscheidung identisch vs. divergent, ggf. Nutzerbestätigung im App-Layer) statt stillem Overwrite; atomares Write zusätzlich. Die Brick-Richtung (b) bleibt in jedem Fall eine Schwachstelle.
- **Priorität:** HIGH
- **Status Phase B:** CONFIRMED+FIXED — Silent Overwrite bewiesen (divergenter Re-Import mit gültiger Ed25519-Signatur → Ok + Datei ersetzt); Fix: Konflikt-Detection (byte-identisch = idempotent Ok, divergent = ValidationError) + atomarer tmp+rename-Write in `import_voucher_standard` (AUDIT-M03-004), Suite 14/14 grün.

## H-03-3 — Keine Evaluations-Budgets: Stack-Overflow & CPU/Memory-Exhaustion durch craftete CEL-Ausdrücke
- **Vermutung:** `evaluate_rule` setzt KEINEM Schritt Ressourcenlimits: weder `Program::compile`/`cel_parser::parse`, noch dem handgeschriebenen rekursiven Descent `eval_and_check_ast`, noch der Interpreter-Ausführung. Drei konkrete Erschöpfungsvektoren: (1) **Stack-Overflow (Abort):** tief geschachtelte Ausdrücke (hunderttausendfach `!`/`(`/`[`) treiben die Rekursion in `cel_parser::Parser` und/oder `eval_and_check_ast` (~L69–432) über den Thread-Stack → Prozess-Abort, NICHT abfangbar als `Err`; jede Validierung eines Bundles gegen so einen Standard killt die gesamte Wallet-Anwendung. (2) **Quadratische Comprehension-Kosten:** `Expr::Comprehension` klontt pro Iteration die GESAMTE Environment inkl. Voucher-State (`loop_env = env.clone()`, ~L412); ein Regel-Ausdruck `Voucher.items.all(i, i.x == 1)` über eine vom Angreifer beeinflusste große Liste (Vouchers mit vielen Signaturen/Einträgen) kostet O(n²) Speicher/Kopien. (3) **Doppel-Auswertung:** Jede Regel wird komplett zweimal evaluiert (AST-Pre-Check + echter Interpreter, evaluate_rule L40 + L55), was jeden Cost-Faktor verdoppelt. Da Ausdrücke aus dem signierten `[immutable]`-Block kommen, ist der Threat Model primär bösartiger/compromisster Issuer bzw. social-engineered `.standard`-Files — aber Modul 00 (Wallet-DoS) listet CPU/Memory-Exhaustion explizit als System-Albtraum.
- **Betroffene Invariante:** Fail-Closed & Verfügbarkeit: Ressourcenerschöpfung darf nie zu Abort/Hang führen (Panic-Freiheit auf untrusted Input ist Projektgrundsatz); Determinismus (#1) kollabiert, wenn Evaluation zeitlich unbeschränkt ist.
- **Zielcode:** src/services/dynamic_policy_engine.rs :: eval_and_check_ast (~L69–432, Rekursionsbasis) + Expr::Comprehension-Zweig (~L407–428, env.clone pro Iteration) + evaluate_rule (~L20–65, keine Budget-Parameter)
- **Geplanter Fail-First-Test:** (a) `assert!(matches!(DynamicPolicyEngine::evaluate_rule(&"!".repeat(200_000) + "true", &json!({}), None), Err(_)))` — unpatched stürzt der Testprozess mit Stack-Overflow ab (Test FAIL hard). (b) Budget-Assert: Voucher-State mit 50.000-Element-Array + Regel `Voucher.items.all(i, i.x == 1)`; `assert!(duration < Duration::from_secs(5))` bzw. zukünftiges API `evaluate_rule_bounded(...)` liefert `Err(EvaluationError("budget exceeded"))` — auf unpatched Code läuft die Auswertung O(n²)-env-clones deutlich über jedes Budget.
- **Triage-Vorabcheck:** „CEL-Engine der Third-Party-Library, kein Budget“ ist kein Design-Requirement, sondern eine bekannte Library-Limitation; die Pre-Check-Schicht ist projekt-eigen und der natürliche Ort für Depth-/Node-Count-Guards. Ein grober statischer Guard (max AST-Tiefe/max Nodes beim Standard-Import in `verify_and_parse_standard`) wäre sogar standard-konform. Nicht intentional.
- **Priorität:** HIGH
- **Status Phase B:** CONFIRMED+FIXED — Crash-Kliff empirisch bei Klammer-Tiefe 12(ok)/16(SIGABRT) gemessen; Fix: statischer Pre-Scan (Länge ≤4096, Tiefe ≤8, Quote-aware) VOR Program::compile + AST-Rekursionslimit 512 + Comprehension-Budget 1000 Iterationen in `eval_and_check_ast` (AUDIT-M03-005). Teilvektor "unary chains" = FALSE POSITIVE (cel-parser kollabiert `!!!` zu einem Call-Knoten, keine Rekursion). Suite 16/16 grün; Regressionstest lib+integration_tests 498/498.

## H-03-4 — Zahlen-Domänen-Drift beim Context-Mapping: Int/UInt/Fallback-f64-Koercion mit Präzisionsverlust
- **Vermutung:** `json_to_cel` mappt JSON-Numbers in Reihenfolge i64→`Value::Int`, u64→`Value::UInt`, sonst f64→`Value::Float` (dynamic_policy_engine.rs:439–451). Zwei Risiken: (1) Zahlen jenseits des u64-Bereichs oder mit Bruchteil werden still in f64 koerziert (Präzisionsverlust > 2^53 mantissa bits) — ein Regel-Vergleich über solche Werte kann je Richtung falsch-positive/-negative Ergebnisse liefern, ohne dass ein Fehler entsteht. (2) Asymmetrie zwischen AST-Pre-Check (serde_json `Number`: unterscheidet PosInt/Float strikt, `_==_` ~L305–313) und cel-interpreter (möglicherweise cross-type numeric equality/coercion zwischen `Int`/`UInt`/`Float`): Der Pre-Check kann ein Ergebnis berechnen, das NICHT dem tatsächlichen Interpreter-Ergebnis entspricht. Solange alle Modellfelder `String`/kleine Ints sind, ist die Angriffsfläche heute klein — aber `json_to_cel` ist öffentlich erreichbarer Mapping-Code für den gesamten `Voucher`/`Transaction`-JSON-Baum; ein später hinzugefügtes u64/u128-Feld (Timestamps, Nonces) aktiviert den Pfad automatisch und unsichtbar. M03-001/M03-002 decken Bracket-Null und `check_decimals`-Wraparound ab, NICHT diese Koercionskette.
- **Betroffene Invariante:** 100 % deterministische CEL-Auswertung (#1) — Präzisionsverlust und Plattform-unterschiedliche f64-Routinen brechen Reproduzierbarkeit; sekundär Fail-Closed, wenn Koercion Fehler zu Vergleichen macht.
- **Zielcode:** src/services/dynamic_policy_engine.rs :: json_to_cel (~L435–452, f64-Fallback L445–446) vs. eval_and_check_ast Literal-Zweig (~L78–95)
- **Geplanter Fail-First-Test:** Invariantentest auf exakte Zahlenerhaltung: Voucher-State mit `{"big": 18446744073709551615}` und Grenzwert-nahen Werten; `assert!(!matches!(evaluate_rule("Voucher.big < 9223372036854775808", ...), Ok(true)))` bzw. Assert, dass UInt-exakte Gleichheit gilt: `evaluate_rule("Voucher.big == 18446744073709551615", ...) == Ok(true)` und dass KEIN Pfad über Float geht (per Debug-Verifikation des gemappten `Value`). Auf unpatched Code schlägt mindestens einer der Asserts fehl, wenn cel-interpreter 0.10 Int/UInt-Literale cross-type via f64/i64-Cast vergleicht (Voranalyse nötig; falls grün, als FALSE POSITIVE mit Beweis dokumentieren).
- **Triage-Vorabcheck:** Der u64→UInt-Kommentar („CEL natively supports UInt … for large positive limits“, L443) zeigt Designabsicht; INTENTIONAL wäre höchstens die f64-Fallback-Existenz für Literale. Nicht intentional: stille Koercion ohne Fail-Closed-Fehler für außerhalb der exakten Domäne liegende Werte.
- **Priorität:** MEDIUM
- **Status Phase B:** FALSE-POSITIVE (durch Beweis als Regression-Kontrollen dokumentiert, AUDIT-M03-006): json_to_cel mappt u64 exakt auf UInt; cel-interpreter vergleicht Int↔UInt exakt via try_into (kein f64-Umweg); Plain-Int-Literale >i64::MAX failen laut beim Compile statt still zu koerzieren; f64-Pfad nur für echt gebrochene JSON-Numbers. Kontroll-Tests grün (u64::MAX-Exaktheit, Grenzwert i64::MAX, Float-Determinismus).

## H-03-5 — Determinismus native ↔ wasm32: Float-Pfade in JCS-Kanonisierung und CEL-Mapping
- **Vermutung:** Kern-Invariante ist plattformidentische Auswertung (native/wasm32). Alle kanonisierungrelevanten Strukturen (Standard-Zonen, Voucher, Signatur-Payloads) bestehen aktuell aus Strings/Ints — `to_canonical_json` (RFC 8785 via `serde_json_canonicalizer` 0.3) hat daher nominal keinen Float-Input. Risikostellen: (1) Sobald irgendein Feld als f64 in eine gehashte/gezeichnete Struktur gerät, greift ES6-Number-Formatting — jede Abweichung der Ryu-Implementierung zwischen Targets (oder ein Future-Refactor auf libc-formatierte Pfade) ändere Hashes und damit Signaturvalidierung/Laufzeitverhalten plattformabhängig. (2) Im CEL-Mapping existiert der f64-Pfad (H-03-4); Float-Arithmetik in Regeln (`Voucher.x * 1.1 > y`) wäre IEEE754-f64 und damit zwar deterministisch zwischen native/wasm32, ABER nicht mehr bitidentisch zum AST-Pre-Check (serde_json/f64), was Pre-Check/Interpreter-Divergenzen erzeugt. Es fehlt ein Invariantentest, der GARANTIERT, dass Floats niemals in Kanonisierung oder Regelkontext gelangen können (negativ-getestete Domänen-Grenze statt Vertrauen auf aktuelle Modellfelder).
- **Betroffene Invariante:** 100 % deterministische Auswertung native ↔ wasm32 (#1) und Signatur-Stabilität der Hash-Chain (#3).
- **Zielcode:** src/services/utils.rs :: to_canonical_json (~L24–26) + src/services/dynamic_policy_engine.rs :: json_to_cel (~L435–452)
- **Geplanter Fail-First-Test:** Property-/Invariantentest: (a) Für repräsentative Edge-Structures (u64::MAX, hohe Dezimalstrings, leere Optionen) gilt `get_hash(to_canonical_json(x))` konstant und die kanonische Ausgabe enthält garantiert kein `e`/`E`/Exponential-Format und keinen trailing-Float-Marker: `assert!(!canonical.contains(['e', 'E']) || only_in_strings)`; (b) `assert!(json_to_cel(JsonValue::Number(2^53+1 as u64)) == Value::UInt(exakt))` — kein Float-Umweg. Auf unpatched Code ist (a) derzeit vermutlich grün (False Positive möglich, dann als Domänen-Pinning-Dokumentation behalten); (b) kann rot schlagen, wenn das Mapping über f64 geht.
- **Triage-Vorabcheck:** String-basierte Beträge sind bereits `[INTENTIONAL DESIGN REQUIREMENT]` (kryptographische Stabilität laut AGENTS.md) — die Hypothese zielt nicht auf Änderung davon, sondern auf den fehlenden negativen Invariantentest, der die Float-freie Domäne dauerhaft festschreibt (wasm32-Bindings in `bindings/wasm` machen das real relevant).
- **Priorität:** LOW

## H-03-6 — Fehlende Issuer-Pinning-/Trust-Anker-Bindung über Create-, Receive- und Inspect-Pfade
- **Vermutung:** `verify_and_parse_standard` validiert ausschließlich interne Konsistenz: Die Ed25519-Signatur wird gegen den IM FILE angegebenen `issuer_id` geprüft (standard_manager.rs:60–80) — jeder Key kann jeden Standard signieren. Kein Core-Pfad bindet eine UUID an einen erwarteten Issuer: `create_new_voucher` akzeptiert beliebigen TOML-Content (command_handler.rs:28–30), `receive_bundle` vertraut der vom Aufrufer übergebenen `standard_definitions_toml`-Map (command_handler.rs:97–102), `inspect_voucher_standard_container` liefert den verifizierten Standard ohne Trust-Kontext zurück. Für BESTEHENDE Vouchers verhindert der `standard_definition_hash`-Vergleich (identity.rs:19–25) den Swap effektiv — aber für NEU erstellte Vouchers kann ein Angreifer ein optisch identisches Klon-Standard (gleicher Name „Minuto“, gleiche UUID-Nähe, eigener Key, schwächere Regeln) unterbringen; der Empfänger, der dieses TOML zur Validierung übergibt, akzeptiert dann regulär signierte Vouchers aus dem Klon-Ökosystem. Cross-Swap alter Vouchers gegen das Klon-Standard scheitert am Hash — gut. Offen: Core bietet keine primitive Prüfung „diese UUID war bereits mit Issuer-Key X / Hash H installiert“.
- **Betroffene Invariante:** Immutability & Integrity (#3) auf Ökosystem-Ebene: Authentizität eines Standards ist nur innerhalb einer Datei, nicht über dessen Lebenszyklus (Installation → Erstellung → Empfang) verankert.
- **Zielcode:** src/services/standard_manager.rs :: verify_and_parse_standard (~L29–90, issuer extraction L60) + src/app_service/command_handler.rs :: create_new_voucher (~L21–43) und receive_bundle (~L85–119)
- **Geplanter Fail-First-Test:** Wallet hat Standard A (uuid U, Issuer K1, hash H1) importiert; `create_new_voucher` wird mit Klon-Standard B (uuid U, Issuer K2, hash H2, schwächere `additional_signatures_range`) aufgerufen: `assert!(result.is_err(), "core must refuse voucher creation against a re-signed clone of an already-installed standard uuid")` — auf unpatched code Ok(Voucher gebunden an H2). Alternativ (falls Pinning als App-Layer-Task triagiert wird): Invariantentest, der MINDESTENS dokumentiert/prüft, dass receive/create NIEMALS einen anderen Hash als den installierten für dieselbe UUID akzeptieren, ohne expliziten Update-Call.
- **Triage-Vorabcheck:** Hohe Wahrscheinlichkeit für `[INTENTIONAL DESIGN REQUIREMENT]`: Offline-first, kein Netz, Issuer = Autorität, Trust-Entscheidung bewusst im App-Layer (vgl. design-decisions). Falls triagiert als intentional: NICHTS an Logik ändern; englische Doku der Trust-Grenze in `verify_and_parse_standard` + Invariantentest, der das Hash-Binding gegen Klon-Standards festschreibt (Schutz vor Regression), plus Verweis an App-Layer/Tauri-Wrapper für Pinning-UI.
- **Priorität:** MEDIUM

## WH3-03-301 — Comprehension über Non-Array-Range: `todo!()`-Panic (Prozess-Abort) statt fail-closed
- **Vermutung:** Der AST-Pre-Check behandelt `Expr::Comprehension` nur für Array-Ranges (dynamic_policy_engine.rs:531-558). Für JEDEN anderen Range-Typ liefert der Shim `Ok(JsonValue::Null)` (Zeilen 559-561), OHNE Fehler und OHNE die Kindknoten (`accu_init`, `loop_cond`, `loop_step`, `result`) zu besuchen — fehlende Keys/OOB in Comprehension-Körpern werden also bei Non-Array-Ranges gar nicht validiert und der Ausdruck erreicht unbehindert den Interpreter. Dort endet jede Iteration über einen Nicht-List/Nicht-Map-Range in `t => todo!("Support {t:?}")` (cel-interpreter objects.rs:702) — ein **uncatchbarer PANIC**, kein `Err`. Trigger A (pure literal, kein State nötig): `'abc'.all(x, x == 'a')`. Trigger B (realistisch, jeder Minuto-Voucher): `Voucher.nominal_value.unit.all(c, c == 'M')` — `unit` ist ein String-Feld; der Select liefert String → Shim skippt stumm → Interpreter panict bei `program.execute`. Da `all/exists/map/filter` syntaktische Makros sind (cel-parser macros.rs:21-29 akzeptiert JEDES target), genügt eine signierte Regel mit solchem Ausdruck, um die GESAMTE Wallet beim Validieren von Create/Receive/Transfer abzuschießen (Panic ist nicht als Err abfangbar; kein catch_unwind im Aufrufpfad rules.rs:32-36). Sekundärtrigger derselben Klasse: `Expr::Struct`-Literale (`Typ{field: val}` laut Grammar parsebar) fallen in den Shim-Catch-All (dynamic_policy_engine.rs:563, kein Kindbesuch) und panichen im Interpreter via `todo!("Support structs!")` (objects.rs:706). Die M03-005-Budgets schützen NICHT davor: Länge/Tiefe solcher Ausdrücke sind winzig.
- **Betroffene Invariante:** Fail-Closed Principle (#2): Ein nicht auswertbarer Ausdruck MUSS `Err` liefern, niemals Prozess-Abort; projektweiter Grundsatz „Panic-Freiheit auf untrusted Input“ (Signierte Standards + Angreifer-influenzierbarer Voucher-State sind Threat Model, vgl. M03-005-Triage).
- **Zielcode:** `src/services/dynamic_policy_engine.rs` :: `eval_and_check_ast`, Arm `Expr::Comprehension` (Else-Zweig ~L559-561) + Catch-All ~L563; Panic-Quelle: cel-interpreter-0.10.0 `src/objects.rs` L702/L706.

## WH3-03-302 — Determinismus-Bruch: Map-Range-Comprehension iteriert HashMap in zufälliger Reihenfolge
- **Vermutung:** Für Map-Ranges gilt dieselbe Shim-Lücke wie WH3-03-301 (Ok(Null)-Skip ohne Kinderprüfung, dynamic_policy_engine.rs:559-561) — ABER der Interpreter unterstützt Maps: er iteriert `map.map.deref().keys()` (objects.rs:692-701) über eine rohe `HashMap<Key, Value>` (objects.rs:16-18, Default-RandomState) — die Iterationsreihenfolge ist pro Map-Instanz ZUFÄLLIG und plattform-/laufzeitabhängig. Über das `map`-Makro auf einem Map-Literal wird daraus ein nicht-deterministischer Policy-Verdict: `{'b':1,'a':2,'c':3}.map(k, k)[0] == 'a'` liefert je Laufzeit unterschiedlich `Ok(true)`/`Ok(false)`. Zusätzlich zählt der Pre-Check für Map-Ranges NULL Iterationen (Skip), d. h. dieser Pfad liegt komplett außerhalb jedes Budgets. State-seitig sind Maps heute durch das typisierte Modell unerreichbar (voucher.rs kennt keine HashMap-Felder), aber Map-Literale IN der Regel sind freigegeben und signierbar. Damit ist die Kern-Invariante „100 % deterministische CEL-Auswertung across all platforms“ (#1) durch legitime Standardsyntax brechbar — ein Retry derselben Validierung kann ein zuvor abgelehntes Ergebnis umdrehen (= Fail-Open-Richtung möglich).
- **Betroffene Invariante:** Deterministische Auswertung native↔wasm32↔Retry (#1); sekundär Fail-Closed (#2), da ein ablehnender Verdict bei Wiederholung kippen kann.
- **Zielcode:** `src/services/dynamic_policy_engine.rs` :: `eval_and_check_ast` Comprehension-Else (~L559-561) und `Expr::Map`-Arm (~L518-529, baut serde_json::Object mit SORTIERTER/insertion-Order ≠ Interpreter-HashMap-Order → zusätzliche Shim/Interpreter-Divergenz); Panic-/Order-Quelle: cel-interpreter-0.10.0 `src/objects.rs` L17, L692-701.
- **Geplanter Fail-First-Test:** Dieselbe Regel `{'b':1,'a':2,'c':3}.map(k, k)[0] == 'a'` 64× auswerten; Soll-Assert (Determinismus-Invariante): alle Ergebnisse identisch ODER Auswertung fehlt fail-closed (`is_err()` erlaubt, gemischte Bools verboten): `let results: Vec<_> = (0..64).map(|_| evaluate_rule(RULE, &json!({}), None)).collect(); assert!(results.iter().all(|r| *r == results[0]), "CEL evaluation must be deterministic")`. Auf unpatched Code mischen sich `Ok(true)`/`Ok(false)` (RandomState-Per-Instanz-Reihenfolge) → Assert FAILT und beweist Nicht-Determinismus.
- **Triage-Vorabcheck:** Kein Design-Requirement erkennbar: Determinismus ist explizite Audit-Invariante #1; Fixrichtung ist fail-closed (Map-Ranges im Pre-Check entweder kinden-treu prüfen oder `Err` liefern) bzw. sortierte Key-Iteration — keine Offline-/Krypto-Funktion hängt daran.
- **Priorität:** HIGH
- **Status Phase B (Wave 3):** CONFIRMED+FIXED (Fix-Phase A-03, Wave 3) — **Testdesign-Korrektur in der Fix-Phase:** Unerwarteter PASS auf unpatched Code untersucht → FALSE-NEGATIVE-Testdesign, KEIN False Positive: Single-Instance-vs-Fixorder-Probe hat Trefferwahrscheinlichkeit 1/6! ≈ 0,14 % (Probe: 2/256), 64 Wiederholungen sehen daher fast immer uniform `Ok(false)`. Geschärft auf Two-Instance-Coin-Flip (`{'a':1,'b':2}.map(k,k) == {'a':1,'b':2}.map(k,k)` — zwei unabhängige RandomState-HashMaps, ~50 % Flip; Messung unpatched: 34/64 gemischt). Fix: Map-Ranges werden wie alle Non-Array-Ranges fail-closed rejected (Engine-Level-Determinismus ohne Vendor-Fork unmöglich); Budget-Bypass damit ebenfalls geschlossen. Control für Array-Comprehensions ergänzt. Suite 24/24 grün (`finding08_...deterministic_or_fail_closed`). Residual: `Expr::Struct`-Panic im Interpreter (todo! "Support structs!") = künftige Wave, gleiche Klasse.
