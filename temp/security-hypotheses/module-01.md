## H-01-01 — Trap-Anchoring-Framing: Schnorr-Beweis bindet nur Kenntnis eines beliebigen m, nicht m an den Sender-Key
- **Vermutung:** `verify_trap` beweist ausschließlich Kenntnis *eines* Skalars m bezüglich Basis X = u·G — es gibt KEINE Bindung von m an `derive_m(sk_sender, prev_hash)` des behaupteten Senders. Wer seinen eigenen (oder einen frei gewählten) Slope m kennt, kann `blinded_id = u·m·G + ID_Opfer` für ein beliebiges Opfer anchorieren und dazu gültige Schnorr-Beweise führen. Diese Beweise verifizieren bei `verify_stored_proofs_against_identity` gegen den Opfer-Punkt — der F05-Fix („ZKPs müssen gegen die claimed identity verifizieren") ist damit umgehbar, da die ZKPs kryptographisch echt sind. Die DleqProof-Infrastruktur (`trap_k_point = sk · hash_to_curve(prev_hash)`, in PrivacyGuards vorhanden) wird im gesamten `ProofOfDoubleSpend`-Fluss NICHT verifiziert; eine Gleichheits-DLEQ (log_P(k) == log_G(ID)) würde das Schließen der Lücke ermöglichen. Gate 4 (lokale Transaktionsverifikation) schützt nur Importe mit lokalem Voucher-Kontext; im NoLocalContext-Pfad bleibt der Proof als „unverified witness note" MIT `offender_id = did:key:Opfer` persistent gespeichert → Reputationsschaden (`TrustStatus::KnownOffender`), Match-4-Verknüpfung über `get_proof_id_for_voucher`, Anzeige gefälschter Attribution.
- **Betroffene Invariante:** Anti-Framing: Ein did:key-Attributionsclaim darf nur möglich sein, wenn die Traps kryptographisch an den Permanent-Key des Offenders gebunden sind (V = u·m·G + ID mit m = derive_m(sk_offender, prev_hash)). Kerninvariante „Identitäts-Rekonstruktion V = u·m + ID" ist nur unter dieser Bindung forensisch belastbar.
- **Zielcode:** src/services/trap_manager.rs :: verify_trap (~247) und verify_stored_proofs_against_identity (~441); src/wallet/conflict_handler.rs :: import_proof Security Gate 3b (~300–357)
- **Geplanter Fail-First-Test:** Angreifer-Keypair erzeugen, beliebiges m' wählen, zwei synthetische Fork-Transaktionen (gemeinsamer prev_hash + gemeinsamer attacker-eigener `sender_ephemeral_pub`, kanonische u_i via `compute_u_input`) mit `blinded_id_i = u_i·m'·G + ID_innocent_point` und zugehörigen Schnorr-Proofs bauen; `ProofOfDoubleSpend { offender_id: did_key_innocent, ... }` mit ehrlicher Reporter-Signatur erstellen und gegen ein Wallet OHNE lokale Kontext-Transaktionen `import_proof` aufrufen. Soll-Invariante: `assert!(wallet.import_proof(proof).is_err())` — Attribution ohne m↔sk-Bindung (bzw. ohne verifizierte trap_k_point-DLEQ gegen den claimed Key) muss abgelehnt werden. Auf unpatched Code kehrt `import_proof` Ok(()) zurück → Test FEHLSCHLAG.
- **Triage-Vorabcheck:** Könnte `[INTENTIONAL DESIGN REQUIREMENT]` sein? Die Doku an `offender_id`/`suspected_identity` behauptet, verifizierte ZKPs seien ausreichendes Anti-Framing — das Design WILL also Bindung an die wahre Identität, nicht beliebige m-Kenntnis. Kein offline Feature ist auf „jeder kennt irgendein m genügt" angewiesen → eher `[CONFIRMED VULNERABILITY]`; Minimal-Fix wäre Verifikation von `trap_k_point` (aus PrivacyGuard/Trap-Erweiterung) als m-Quelle oder Ablehnung did:key-Claims ohne solche Bindung am Import-Rand.
- **Priorität:** CRITICAL
- **Status Phase B:** CONFIRMED-PENDING (Fail-First-Test `f07_trap_anchoring_framing_arbitrary_slope_must_be_rejected` schlug auf unpatched Code FEHL — gefälschtes did:key-Attribut wurde als Witness-Note akzeptiert; Fix erfordert Wire-Format-Erweiterung (trap_k_point+DLEQ), daher Test `#[ignore = "pending architectural fix - see report AUDIT-01-F07"]`, Report dokumentiert Exploit + Remediation).

## H-01-02 — False Dispute Injection: gemischter realer+gegifte-Gossip-Fingerprint erzeugt persistierten did:key-Proof ohne ≥2-Trap-Verifikation
- **Vermutung:** In `verify_and_create_proof` wird `offender_id` direkt aus `conflicting_transactions[0].sender_id` übernommen (~567), OHNE dass der ≥2-verifizierte-Traps-Check läuft — die De-Anonymisierungs-/Verifikationslogik greift nur im Zweig `offender_id == ANONYMOUS`. Szenario: Angreifer liefert per Gossip/Bundle-Header einen Fingerabdruck mit dem öffentlich bekannten ds_tag einer echten, lokal gehaltenen Sende-Transaktion T_S des Opfers und einem neuen t_id-Wert. `check_for_double_spend` stuft das als `verifiable_conflicts` ein (local_history enthält den Tag); `verify_and_create_proof` findet T_S lokal, setzt `offender_id = <did:key des Opfers>` und erzeugt aus [T_S + synthetischem soft_placeholder] einen **persistierten** Proof, der das Opfer als Täter benennt (transaction_handler ~637 speichert ihn). Der F01-Fix verhindert zwar die Quarantäne (poisoned t_id ist nicht lokal), aber das falsche Konflikt-Attribut wird lokal gespeichert, erzeugt Events/UI-Zeilen und kann exportiert werden — False-Dispute-Injection über F01/F05 hinaus.
- **Betroffene Invariante:** „Unverifizierte Daten dürfen keine sicherheitsrelevanten Zustände erzeugen": Ein did:key-offender-Claim in einem gespeicherten Proof erfordert mindestens zwei kryptographisch verifizierte Trap-Proofs — auch (gerade) auf dem lokalen Erzeugungspfad, nicht nur am Import-Gate 3b.
- **Zielcode:** src/wallet/conflict_handler.rs :: verify_and_create_proof (~566–570, Ersetzung offender_id ohne Trap-Check) und src/services/conflict_manager.rs :: create_proof_of_double_spend (~356); Persistierung: src/wallet/transaction_handler.rs (~629–639)
- **Geplanter Fail-First-Test:** Wallet mit einer echten gesendeten Transaktion T_S (Trap vorhanden) bestücken; via `process_received_fingerprints`/`import_foreign_fingerprints` einen Poison-Fingerprint (ds_tag == T_S.ds_tag, neuer t_id, attacker-kontrolliertes u/blinded_id) injizieren; Bundle-/Konfliktverarbeitung anstoßen. Soll-Invariante: `assert!(wallet.list_conflicts().iter().all(|c| c.offender_id != victim_did))` bzw. kein persistierter Proof mit `conflicting_transactions.len() < echte verifizierbare Traps ≥ 2`. Auf unpatched Code existiert der Eintrag → Test FEHLSCHLAG.
- **Triage-Vorabcheck:** Könnte `[INTENTIONAL DESIGN REQUIREMENT]` sein? Soft Proofs sind als Beweisnotizen gewollt, aber die Doku an `offender_id` schreibt die ≥2-Regel explizit als Anti-Framing-Invariante fest; ein Erzeugungspfad, der sie ignoriert, widerspricht der eigenen Spezifikation → `[CONFIRMED VULNERABILITY]` wahrscheinlich. Falls reine Witness-Notes als unkritisch eingestuft werden, wäre zumindest `offender_id` auf Anonymous/ephemeral zu begrenzen (dann Teil-Fix).
- **Priorität:** HIGH
- **Status Phase B:** CONFIRMED+FIXED (Fail-First-Test `f08_poison_fingerprint_must_not_persist_local_did_key_offender_claim` schlug FEHL — Proof mit offender_id = Opfer-did:key wurde persistiert; Fix: did:key-Kandidaten aus `conflicting_transactions[0].sender_id` werden in `verify_and_create_proof` vor Attribution via `verify_stored_proofs_against_identity` geprüft und sonst auf ANONYMOUS heruntergestuft; Modulfilter 7/7 + alte Suite 6/6 grün).

## H-01-03 — Identitäts-Rekonstruktion: delta_v == 0 (identische blinded_ids) liefert Ok(angreifergewählter Punkt) statt Fehler
- **Vermutung:** `extract_id_point_from_raw_data` guardt `delta_u == 0` doppelt, aber NICHT `delta_v == 0`. Für V1 == V2 (byte-identische blinded_ids, beliebige verschiedene kanonische U) ergibt die Formel ID = V1 − (0 · Δu⁻¹) = V1 — die Funktion gibt also erfolgreich genau den Angreifer-Punkt V1 zurück statt abzubrechen. Über Gossip-Fingerprints voll angreiferkontrollierbar; Ergebnis fließt in `verify_and_create_proof` ein, wo `VerifyingKey::from_bytes` meist succeediert und `suspected_identity` (advisory, UI-Manual-Sanctions) auf einen reinen Angreifer-Wert gesetzt wird. Verwandter Grenzfall: V-Punkte niedriger Ordnung/Identitätspunkt werden von `decompress()` akzeptiert. Verletzung des offenen Prüfvektors „falsche Attribution statt Fehler".
- **Betroffene Invariante:** Degenerate Fork-Daten (keine echte Differenz in V) müssen zu einem harten Fehler führen — niemals zu einem erfolgreichen, semantisch bedeutungslosen Identitätspunkt (Kerninvariante: Rekonstruktion nur bei genuine fork V1 ≠ V2).
- **Zielcode:** src/services/trap_manager.rs :: extract_id_point_from_raw_data (~404–422, fehlender `delta_v == Scalar::ZERO`-Guard neben dem vorhandenen `delta_u`-Guard)
- **Geplanter Fail-First-Test:** Zwei Trap-Tripel mit identischen V-Bytes (gültiger Curve-Punkt, z. B. Basepoint) und verschiedenen kanonischen U bauen; `assert!(extract_id_point_from_raw_data(...).is_err(), "identical blinded_ids must be rejected as degenerate fork")`. Auf unpatched Code wird Ok(V1) geliefert → Test FEHLSCHLAG. (Analog-Test optional: low-order V → Err.)
- **Triage-Vorabcheck:** Könnte `[INTENTIONAL DESIGN REQUIREMENT]` sein? Nein — der existierende `delta_u`-Guard dokumentiert exakt die gegenteilige Designabsicht („dalek's invert() silently returns zero … bogus identity point"); der fehlende `delta_v`-Fall ist eine Asymmetrie, kein Design. Impact durch advisory-only-Nutzung begrenzt, daher MEDIUM statt HIGH.
- **Priorität:** MEDIUM
- **Status Phase B:** CONFIRMED+FIXED (Fail-First-Test `f09_extract_id_rejects_identical_blinded_ids` lieferte auf unpatched Code Ok(V1) — mit vollständigen 32-Byte-Kanonical-Scalaren; Fix: `delta_v.is_identity()`-Guard in `extract_id_point_from_raw_data`; Modulfilter 8/8 + alte Suite 6/6 grün). Randnotiz: der ältere Guard-Test `guard_extract_id_rejects_identical_u` bestand bisher nur zufällig (4-Byte-U wird an der Längenprüfung abgewiesen, nicht am Identical-U-Guard) — Assertion bleibt korrekt, aber aus schwächerem Grund; im Report vermerkt. Regression: `identity_trap_audit::test_extracted_point_validity_check` nutzte V1==V2 zufällig als Bequemlichkeit — minimal angepasst (degenerater Fall wird jetzt geassertet, Downstream-Checks laufen mit echten V1≠V2); Suite 62/62 grün.

## H-01-04 — Kanonisierungs-Desync: derive_proof_id (erstes Match, unsanitized) vs. get_pubkey_from_user_id (rfind, whitespace-sanitized)
- **Vermutung:** `derive_proof_id` sucht das ERSTE Vorkommen von `"@did:key:z"` (`find`) und nutzt den Roh-String ohne Whitespace-Sanitization, während `get_pubkey_from_user_id`/`get_prefix_from_user_id` am LETZTEN `@` splitten und `sanitize_user_id` anwenden. `import_proof` ruft niemals `validate_user_id` auf. Folge: (a) Render-Varianten desselben Keys (eingeschobene Leerzeichen/Newlines wie in den sanitize-Tests von crypto_identity) erzeugen verschiedene `proof_id`s für denselben logischen Konflikt → die Immunity-/Dedup-Regel („Proof schon bekannt → ignorieren", key = proof_id) wird umgangen; derselbe Konflikt mehrfach importierbar (Duplicate-Entries, Auflösungs-Splitting). (b) Attributions-Gate 3b und proof_id-Konsistenzcheck operieren auf unterschiedlichen Byte-Repräsentationen desselben offender_id-Strings — ein Desync, der bei künftigen Parser-Änderungen zum Öffnen framing-relevanter Lücken einlädt.
- **Betroffene Invariante:** Deterministische, kanonische proof_id-Ableitung: `proof_id = SHA3-256(offender_pk_bytes || fork_prev_hash)` muss eindeutig vom kanonischen Offender-Key abhängen; Dedup/Immunity keyed on proof_id setzt Kanonizität voraus.
- **Zielcode:** src/services/conflict_manager.rs :: derive_proof_id (~217–239, `.find("@did:key:z")` + `offender_id.as_bytes()`-Fallback ohne Sanitization) vs. src/services/crypto_identity.rs :: get_pubkey_from_user_id (~202–241, rfind + sanitize_user_id); Konsument: src/wallet/conflict_handler.rs :: import_proof (~280–298)
- **Geplanter Fail-First-Test:** Einen gültigen Proof mit offender_id = `did:key:z<KEY>` bauen und importieren (Ok); dann byte-gleiches Proof-Objekt mit offender_id = `did:key:z <KEY>` (eingeschobenes Space, von get_pubkey sanitisiert) mit entsprechend angepasster reporter_signature über den neuen proof_id ableiten und importieren. Soll-Invariante: `assert_eq!(first_proof_id, second_proof_id)` bzw. zweiter Import muss via Immunity ignoriert werden (`proof_store.proofs.len()` unverändert). Auf unpatched Code entstehen zwei Entries → Test FEHLSCHLAG.
- **Triage-Vorabcheck:** Könnte `[INTENTIONAL DESIGN REQUIREMENT]` sein? Kaum — AUDIT-01-F03 hat bereits dokumentiert, dass Kanonizität der Feldformate Voraussetzung für Hash-Stabilität ist; hier ist die offender_id-Kanonizität gerade NICHT erzwungen. Fix wäre ein einziger `validate_user_id`-Gate vor derive_proof_id (Fail-closed). Impact ohne H-01-01 begrenzt (Dedup/DoS/display), daher MEDIUM.
- **Priorität:** MEDIUM
- **Status Phase B:** CONFIRMED+FIXED (Fail-First-Test `f10_proof_id_must_be_canonical_across_offender_render_variants` — Render-Varianten (`"anonymous "` vs `"anonymous"`) erzeugten verschiedene proof_ids, Immunity/Dedup umgehbar; Fix: `derive_proof_id` kanonisiert offender_id identisch zu `get_pubkey_from_user_id` (Whitespace-Strip + `rfind("@did:key:z")`), kanonische Inputs byte-kompatibel; Modulfilter 9/9 + alte Suite 6/6 grün).

## H-01-05 — process_l2_verdict: optionale expected_ephemeral_pub-Prüfung + Legacy-Ok-Downgrade ermöglichen Server-seitige False Quarantine / False Confirm
- **Vermutung:** In `process_l2_verdict` ist Schritt 2 (Abgleich des gemeldeten `sender_ephemeral_pub` mit der lokal erwarteten Key) an `if let Some(expected)` gebunden — beim API-Aufruf mit `expected_ephemeral_pub = None` entfällt die Anti-Framing-Sperre komplett: ein böswilliger/kompromittierter L2-Server kann ein envelope-signiertes `Verified { lock_entry }` mit FREMDEM ephemeral Key und fremdem t_id liefern (die lock_entry-Signatur stellt der Angreifer selbst), und der Client liefert `VerdictAction::TriggerQuarantine(foreign_t_id)` → lokale Quarantäne des eigenen aktiven Vouchers. Zusätzlich mappt der Legacy-Fallback `L2Verdict::Ok { .. }` (~408) NUR auf Envelope-Signatur ohne jegliche Content-Bindung an Challenge/ds_tag/t_id → ein „Ok" bestätigt lokal, ohne dass der Server den konkreten Lock je geprüft haben muss (Downgrade-Pfad für Double-Spend-Meldungen). Der produktive Call (l2_facade ~108) übergibt zwar Some(..), aber die Core-API erlaubt None und der `Ok`-Pfad gilt für beide.
- **Betroffene Invariante:** Quarantäneentscheidungen dürfen nur aus Beweisen folgen, die kryptographisch an den lokalen Transaktionskontext gebunden sind (ds_tag, t_id, sender_ephemeral_pub) — ungebundene Serveraussagen dürfen keinen Status-Mutation auslösen.
- **Zielcode:** src/services/l2_gateway.rs :: process_l2_verdict (~379–396 optionaler Key-Abgleich; ~408–411 Legacy-Ok-Fallback)
- **Geplanter Fail-First-Test:** (1) Gültig server-signiertes Envelope `Verified { lock_entry }` mit fremdem sender_ephemeral_pub/fremdem t_id an `process_l2_verdict` mit `expected_ephemeral_pub = None` → Soll: `assert!(result.is_err())` bzw. kein TriggerQuarantine ohne Key-Bindung. (2) Envelope `L2Verdict::Ok { signature }` (valide Server-Sig) zu einer Challenge, für die lokal ein echter Konflikt bekannt ist → Soll: kein `ConfirmLocal` ohne lock_entry-Bindung. Auf unpatched Code werden beide Aktionen geliefert → Tests FEHLSCHLAGEN.
- **Triage-Vorabcheck:** Könnte `[INTENTIONAL DESIGN REQUIREMENT]` sein? Der `Ok`-Varianten-Kommentar sagt selbst „Deprecated/Fallback (should be replaced by Verified)" — kein aktiv verteidigtes Design. Der None-Pfad könnte als „Host entscheidet selbst" argumentiert werden; dann wäre Mindestmaß ein Debug-Assert/Dokumentation. Da l2_server_pubkey wallet-lokal konfiguriert wird (semi-trusted), eher MEDIUM als HIGH.
- **Priorität:** MEDIUM

## WH3-01-101 — Cross-Voucher False Quarantine durch Bucket-Stuffing über `import_foreign_fingerprints` (Map-Key-Desync + bedingungsloses Local-Candidate-Trust)
- **Vermutung:** `import_foreign_fingerprints` übernimmt den attacker-kontrollierten JSON-Map-Key als Bucket-Schlüssel (`entry(hash)`, conflict_manager.rs ~663–667), statt nach `fp.ds_tag` neu zu keyen — jeder andere Ingest-Pfad (`process_received_fingerprints` ~1065, `scan_and_rebuild_fingerprints`) keyt korrekt nach Inhalt. Ein Angreifer liefert einen Export-Blob `{K: [fp_A, fp_B]}` mit zwei kryptographisch ECHTEN, die Ingress-Gates einzeln passierenden Fremd-Fingerprints (aus Gossip kopiert: gültige `layer2_signature`, echte ds_tags zweier VERSCHIEDENER Voucher des Opfers) unter einem willkürlichen Schlüssel K. Folge: `check_for_double_spend` sieht `unique_t_ids == 2` in einem Bucket → verifiable_conflict; in `resolve_conflict_offline` sind BEIDE Kandidaten `local_t_ids` (beide tx existieren lokal im VoucherStore des Opfers!) und nehmen damit UNBEDINGT am Earliest-Wins-Race teil (~1207: `local_t_ids.contains(&fp.t_id) || ...`) — ohne jeden ds_tag/prev_hash-Konsistenzcheck zwischen Bucket-Mitgliedern. fp_B wird mit dem FALSchen prev_hash (dem von tx_A, ~1137 `conflicting_txs[0].prev_hash`) dekodiert → dekryptierter Timestamp ≈ uniform(2^128) → verliert das Race mit Wahrscheinlichkeit ≈ 1−5e−21 gegen den echten Timestamp von fp_A → Write-Phase (~1242–1259) quarantänt die Instanz von tx_B (`"Lost offline race"`), obwohl dort nie eine Double-Spend vorlag. Mindestens einer von zwei unschuldigen aktiven Vouchern wird garantiert quarantänt; der Angriff ist remote, gate-konform (alle Signaturen echt) und reanimiert den F01-Impact über die nie auditierte Import-Boundary. Zusätzlich kann der Winner eine zuvor (z.B. per L2-Verdict) Quarantäne-Instanz zurück auf `Active` setzen (siehe WH3-01-105).
- **Betroffene Invariante:** „Unverifizierte/nicht kollidierende Daten dürfen keine Status-Mutation auslösen": Eine Quarantäne darf nur folgen, wenn alle Race-Kandidaten nachweislich denselben Input teilen (ds_tag == H(prev_hash || sender_ephemeral_pub) für JEDEN Kandidaten, auch lokale); Fingerprintf-Buckets müssen inhaltlich kohärent sein (Bucket-Key == fp.ds_tag).
- **Zielcode:** `src/services/conflict_manager.rs` :: import_foreign_fingerprints (~663–667, fehlendes Re-Keying/Key-Validierung); `src/wallet/conflict_handler.rs` :: resolve_conflict_offline (~1146–1211 Kandidatenfilter trustet lokale t_ids bedingungslos; ~1137 prev_hash aus conflicting_txs[0]; ~1242–1259 Write-Phase)
- **Geplanter Fail-First-Test:** Wallet mit zwei aktiven Vouchern (bestehende Fixtures); deren echte Fingerprints aus `export_own_fingerprints`/Scan entnehmen; Blob `{"stuffkey": [fp_A, fp_B]}` bauen und `wallet.import_foreign_fingerprints()` aufrufen; Konfliktverarbeitung anstoßen (public receive-Pfad wie im F01-Test). Soll: `assert!(beide Instanzen weiterhin Active)` bzw. kein verifiable_conflict mit gemischten ds_tags. Auf unpatched Code wird eine Instanz `Quarantined{Lost offline race}` → Test FEHLSCHLAG.
- **Triage-Vorabcheck:** Kein dokumentiertes Design; das systemweite Grouping-Invariante (Key == ds_tag) wird überall sonst erzwungen — `[CONFIRMED VULNERABILITY]` wahrscheinlich. Kein Offline-Feature hängt an „fremde Buckets beliebig mischen".
