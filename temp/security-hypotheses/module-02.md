## H-02-1 — Creator-Attribution nicht kryptografisch an Signatur gebunden
- **Status Phase B:** CONFIRMED+FIXED — Test `audit_02_04_forged_creator_attribution_must_be_rejected_in_signature_validation` schlug auf unpatched Code fehl; Fix in `signatures.rs::verify_signatures` (Rollen-/Key-Bindung gegen `creator_profile.id`, Raw-Key-Vergleich) lässt Suite wieder grün.
- **Vermutung:** `verify_signatures` validiert jede `VoucherSignature` ausschließlich gegen den in der Signatur selbst eingebetteten `signer_id`-Key. Es gibt **keine Prüfe**, dass der Key der Rolle `"creator"` kryptografisch zu `voucher.creator_profile.id` passt. Der ErrorCode `CreatorAsAdditionalSigner` (`src/error.rs:318`) existiert, wird aber **nirgends im Codebase ausgelöst**. Ein Angreifer kann einen vollständig selbskonsistenten Voucher bauen: `creator_profile.id = <Opfer-did:key>` (reiner String, geht in `voucher_id`-Hash ein), während die Creator-Signatur unter dem EIGENEN Angreifer-Key steht. Alle Stufen passieren: `verify_voucher_hash` ✓ (Content inkl. Opfer-ID), t_id/prev_hash-Kette ✓, `seen_signers`-Dedupe ✓ (nur 1 Entry), Rollen-Whitelist ✓ (`role == "creator"` überspringt sogar die `allowed_roles`-Prüfung, signatures.rs:33). Folge: Guaranty-/Reputations-Fraud — Voucher behauptet, das Opfer sei Creator/Garant. Zusätzlich möglich: zwei `"creator"`-Signaturen verschiedener Keys, da die Rolle von Dedupe und Whitelist nie mit `creator_profile.id` abgeglichen wird.
- **Betroffene Invariante:** Public-Key-Firewall / kanonische Attribuierung: „Eine Identität kann einem Container nicht unter fremder Attribution zugeordnet werden“; Kern-Invariante „Role Obfuscation Defense“ (Creator-Rolle nur vom echten Creator-Key).
- **Zielcode:** `src/services/voucher_validation/signatures.rs` :: `verify_signatures` (~32–67); Sekundär: `src/services/voucher_manager/creation.rs` :: `create_voucher` (~272), `src/error.rs` :: `CreatorAsAdditionalSigner` (~318, toter Code)
- **Geplanter Fail-First-Test:** Voucher gemäß obigem Rezept bauen (Opfer als `creator_profile.id`, gültige Creator-Signatur des Angreifers via `complete_and_sign_detached_signature`-Schema): `assert!(verify_signatures(&voucher, &standard).is_err())` → schlägt auf unpatched Code FEHL, weil aktuell `Ok(())` zurückkommt.
- **Triage-Vorabcheck:** Könnte `[INTENTIONAL DESIGN REQUIREMENT]` sein? Kaum — der existierende, aber ungenutzte `CreatorAsAdditionalSigner`-Error belegt, dass die Bindung beabsichtigt war. Zu klären wäre nur, ob Root-vs.-Prefix-SAI desselben Keys erlaubt sein soll (Key-Vergleich statt String-Vergleich nötig).
- **Priorität:** HIGH

## H-02-2 — Seal-Login verwendet selbst-referenziellen Trust-Anker
- **Vermutung:** `verify_seal_on_login` übergibt `&record.seal.payload.user_id` als BOTH `expected_user_id` UND `expected_pubkey_user_id` an `verify_seal_integrity`. Damit wird der Public Key zur Signaturprüfung **aus dem zu verifizierenden Payload selbst** extrahiert: Check 2 (UserMismatch) ist zirkulär immer erfüllt, und jeder beliebigige Angreifer-Key, der einen selbskonsistenten Seal signiert hat, besteht die Integritätsprüfung als `Valid`/`LegacyValid`. Die Signaturprüfung bindet den Seal im Login-Pfad nicht an die Wallet-Identität; der gesamte Schutz reduziert sich auf den nachgelagerten `state_hash`-Vergleich. `LegacyValid` führt zudem zur stillen Re-Binding-Migration (`migrate_seal_on_login`). Im Kontrast: `compare_remote_seal` (seal_handler.rs:320–323) bindet korrekt an `identity.user_id`.
- **Betroffene Invariante:** WalletSeal als Rollback-/Clone-Guard: Signatur muss Seal an Wallet-Identität ankern; `SealValidationResult::UserMismatch`/`InvalidSignature` muss im Login-Pfad überhaupt erreichbar sein.
- **Zielcode:** `src/app_service/seal_handler.rs` :: `verify_seal_on_login` (~431–437); Sekundär: `src/services/seal_manager.rs` :: `verify_seal_integrity` (~111–161)
- **Geplanter Fail-First-Test:** Gültigen Seal einer FREMD-Identität B (payload.user_id = B's ID, korrekt von B signiert) lokal platzieren und `SealManager::verify_seal_integrity(&seal_B, &seal_B.payload.user_id, &seal_B.payload.user_id, instance)` aufrufen (exakt die Login-Semantik): Soll-Verhalten `assert_eq!(result, UserMismatch)` bzw. Ablehnung — aktuell kommt `Valid` zurück → Test FEHLSCHLAG.
- **Triage-Vorabcheck:** Könnte `[INTENTIONAL DESIGN REQUIREMENT]` sein? Teilweise denkbar (Legacy-Wallets ohne bekannte ID müssen ladbar bleiben; `LegacyValid`-Pfad). Aber: Die Identität liegt im Login-Kontext (`identity.user_id` nach Unlock) vor und wird in `migrate_seal_on_login` bereits benutzt — die Selbst-Referenz ist daher vermutlich ein Bug, kein Design. Impact begrenzt, solange `state_hash` nicht fälschbar ist (verschlüsselter Fingerprints-Store) → Defense-in-Depth-Bruch.
- **Priorität:** MEDIUM

## H-02-3 — compare_seals verschluckt echte Forks bei Nonce-Distanz > +1
- **Status Phase B:** CONFIRMED-PENDING — Fail-first bewiesen (`audit_02_05_divergent_chain_at_unverifiable_nonce_distance_must_be_fork`, aktuell `RemoteIsNewer` statt `ForkDetected`), aber Fix erfordert Chain-Walk über L2-Seal-Historie (Single-Seal-Sync-Architektur) → Test `#[ignore = "pending architectural fix - see report"]`; Control-Test pinnt den strikten Direkt-Nachfolger-Zweig.
- **Vermutung:** Für gleiche Epochen gilt: Ist `remote.tx_nonce > local.tx_nonce + 1`, wird **ohne jegliche Hash-Chain-Prüfung** `RemoteIsNewer` zurückgegeben (und symmetrisch `LocalIsNewer`), obwohl `prev_seal_hash` nicht auf die eigene Kette zurückführt (seal_manager.rs:271–274, 282–284 — Kommentar gibt es selbst zu: „Cannot be directly verified -> heuristic“). Genau der dokumentierte Multi-Device-Fork-Fall (geklontes Wallet, beide Devices haben den Key, divergente Ketten mit Distanz ≥ 2) wird damit als legitimer Vorsprung interpretiert. `compare_remote_seal` setzt nur bei `ForkDetected` den Hard Lock (seal_handler.rs:375–379) → Fork bleibt unentdeckt, Pull/Push läuft weiter, Double-Spend-Fenster öffnet sich. DeviceMismatch des Remote-Seals wird bewusst toleriert („OK for comparison“, seal_handler.rs:328–330), sodass der Clone-Fall gerade nicht anders abgefangen wird.
- **Betroffene Invariante:** ForkDetected-Hard-Lock-Garantie: „Hash chains do not match, even though one side is newer → Triggers a hard lock“ (`models/seal.rs:106–109`) — der Distanz-Heuristik-Zweig bricht genau diese dokumentierte Invariante.
- **Zielcode:** `src/services/seal_manager.rs` :: `compare_seals` (~259–289); Sekundär: `src/app_service/seal_handler.rs` :: `compare_remote_seal` (~373–379). Querverweis Modul 01/04 (Double-Spend-Fenster).
- **Geplanter Fail-First-Test:** Lokaler Seal (nonce=1) plus divergenter Remote-Seal derselben Identität mit nonce=5 und fremdem `prev_seal_hash`: `assert_eq!(SealManager::compare_seals(&local, &remote), SealSyncState::ForkDetected)` → aktuell `RemoteIsNewer` → Test FEHLSCHLAG.
- **Triage-Vorabcheck:** Könnte `[INTENTIONAL DESIGN REQUIREMENT]` sein? Der Code kommentiert die Heuristik bewusst („We trust nonce ordering“), aber sie widerspricht der eigenen Doc-Invariante in `models/seal.rs` und dem Hard-Lock-Zweck. Mindestens Fail-Closed (ForkDetected bei unverifizierbarer Distanz) wäre konsistent; ggf. ist ein Chain-Walk über mehrere Seals nötig.
- **Priorität:** HIGH

## H-02-4 — DetachedSignature-Container ohne `i`-Rebind und ohne Envelope-Signaturprüfung
- **Vermutung:** Der Bundle-Pfad rechnet `container.i` aus den empfangenen Bytes neu und prüft vor allem anderen (`open_and_verify_bundle`, bundle_processor.rs:124–135, Fix HMC-SEC-06-01). Der **DetachedSignature-Pfad tut das nicht**: `process_and_attach_signature` öffnet den Container und prüft niemals (a) dass `i` = H(canonical(content)) gilt, noch (b) dass `container.signature` (falls vorhanden) zum Sender passt. Da `signature` nur über den String `i` geht und `i` nirgends rebindet, ist `(i, signature)` frei transplantierbar: Envelope-Metadaten (`unprotected`, `c`, `et`, `salt`, `recipients`) können getauscht und Container beliebig re-kodiert werden, ohne dass etwas invalidiert wird — Replay/Dedupe-Logik, die auf `i` basiert, ist umgehbar. Bei `EncryptionType::None` (für DetachedSignature explizit erlaubt) bleibt als einzige Barriere die innere Signaturprüfung.
- **Betroffene Invariante:** Container-Seal-Malleability jenseits von Scalar-Fällen: „Container-ID `i` ist kryptografisch an den Inhalt gebunden und wird vor Verarbeitung rebindet“ (vom Bundle-Pfad etablierte Soll-Architektur, asymmetric angewendet).
- **Zielcode:** `src/wallet/signature_handler.rs` :: `process_and_attach_signature` (~146–231); Referenz-Soll: `src/services/bundle_processor.rs` :: `open_and_verify_bundle` (~124–135), `src/services/secure_container_manager.rs` :: `create_secure_container` (~225–233)
- **Geplanter Fail-First-Test:** Gültigen DetachedSignature-Container nehmen, `container.i` (oder `unprotected`) manipulieren, erneut serialisieren: `assert!(wallet.process_and_attach_signature(&identity, &tampered_bytes, None).is_err())` → aktuell `Ok(...)` (Integrität wird nicht geprüft) → Test FEHLSCHLAG.
- **Triage-Vorabcheck:** Könnte `[INTENTIONAL DESIGN REQUIREMENT]` sein? Die innere `validate_detached_signature` deckt Payload-Authentizität ab, aber das rechtfertigt nicht die Asymmetrie zum gehärteten Bundle-Pfad; mindestens der `i`-Rebind ist als Regression der HMC-SEC-06-01-Architektur zu fordern.
- **Priorität:** MEDIUM

## H-02-5 — Empty-Prefix-Form `:checksum@did:key:…` umgeht kanonische Grammatik und aliast auf Root
- **Status Phase B:** CONFIRMED+FIXED — Fail-first bestätigt (`audit_02_06_empty_prefix_and_separator_less_aliases_must_be_rejected`, `:GiD@did:key:z…` wurde akzeptiert); Fix schärft `validate_user_id` auf die exakte `create_user_id`-Grammatik (leerer Prefix UND fehlender `:`-Separator werden jetzt abgelehnt); Crypto-Filter (38 Tests) und Modul-01-Suite grün.
- **Vermutung:** `validate_user_id` akzeptiert IDs der Form `":abc@did:key:zK"`: Vor `'@'` findet `rfind(':')` Position 0 → `prefix=""` → sämtliche Prefix-Format-Checks werden übersprungen (crypto_identity.rs:143–161), und der Checksum-Vergleich läuft gegen `hash("" + did_key_part)` — vom Angreifer öffentlich berechenbar. Solche Strings sind aber über `create_user_id` **unerzeugbar** (`Some("")` liefert nacktes Root-did:key, crypto_identity.rs:77–79) und verletzen damit dieselbe kanonische Grammatik wie der bereits gefixte Doppel-@-Fall (SA02-02) — nur über einen anderen Parser-Pfad. Verschärfend: `get_prefix_from_user_id(":abc@did…")` liefert `None` (leerer Prefix → Root-Äquivalent, crypto_identity.rs:25), d. h. die Form ist eine **Alias-Repräsentation der Root-Identität**, die String-Vergleiche (z. B. chain.rs:512–514 `tx.sender_id != creator_profile.id`, balance.rs:33–37) und Prefix-basierte Schlüsselableitung (`derive_ephemeral_key_pair`-Context-Binding, creation.rs:245) semantisch auseinanderreißen. In Kombination mit H-02-1 ermöglicht das nicht-kanonische Alias-Attributionen, die dedupe-/prefix-seitig nicht vereinheitlicht werden.
- **Betroffene Invariante:** Deterministische Kanonisierung / Public-Key-Firewall: „Nur via `create_user_id` erzeugbare Identitätsstrings dürfen signed Containers betreten; gleiches Key ⇒ gleiche effektive Identität.“
- **Zielcode:** `src/services/crypto_identity.rs` :: `validate_user_id` (~143–167) und `get_prefix_from_user_id` (~18–33)
- **Geplanter Fail-First-Test:** Für einen did:key `D` berechne `ck = last3(bs58(sha3("did:key:…" || D)))` analog Zeile 163–165, baue `format!(":{}@{}", ck, D)`: `assert!(!validate_user_id(&forged))` → aktuell `true` → Test FEHLSCHLAG. Zusätzlich: `assert_eq!(get_prefix_from_user_id(&forged), get_prefix_from_user_id(D))` dokumentiert die Alias-Lücke (Soll: forged-Form gar nicht erst valide).
- **Triage-Vorabcheck:** Könnte `[INTENTIONAL DESIGN REQUIREMENT]` sein? Nein — `create_user_id` kann die Form nicht produzieren; sie verletzt exakt die Invariante, deren Verletzung bei SA02-02 (Doppel-@) bereits als Schwachstelle triagiert und remediert wurde. Gleiche Klasse, anderer Pfad.
- **Priorität:** HIGH

## H-02-6 — Preimage Exposure: `sender_ephemeral_pub` im Klartext vor Transaktionsautorisierung
- **Vermutung:** Der Init-Transaction trägt ab Erstellung den Klartext-Genesis-Anker `sender_ephemeral_pub` (creation.rs:253; models/voucher.rs:152). `create_signing_request` verpackt den **kompletten** Voucher-JSON inklusive dieses Preimages in einen Container an externe Guarantoren (signature_handler.rs:47–56), bevor diese irgendetwas autorisiert oder signiert haben. Empfänger können daraus `u = SHA3-256(prev_hash ‖ sender_ephemeral_pub)` offline rekonstituieren und zukünftige L2-Lock-Requests auf diesen DS-Tag korrelieren/beobachten (De-anonymisierungs-Oracle für Spending-Intent), obwohl die Idle-State-Invariante sonst nur Hash-Commitments (`receiver_ephemeral_pub_hash`) exponiert.
- **Betroffene Invariante:** Privacy/Idle-State: „Ruhende Voucher exponieren nur SHA3-256-Commitments, keine Preimages von Anker-Keys, vor Autorisierung.“
- **Zielcode:** `src/wallet/signature_handler.rs` :: `create_signing_request` (~47–56); Ursprung: `src/services/voucher_manager/creation.rs` (~253), `src/models/voucher.rs` (~152)
- **Geplanter Fail-First-Test:** `create_signing_request(...Cleartext)` → Container öffnen → Voucher-JSON parsen → `assert!(voucher["transactions"][0].get("sender_ephemeral_pub").is_none())` → aktuell `Some(...)` → Test FEHLSCHLAG (beweist Exposure).
- **Triage-Vorabcheck:** Könnte `[INTENTIONAL DESIGN REQUIREMENT]` sein? **Wahrscheinlich ja**: Der Guarantor muss `t_id = H(canonical(tx))` und damit jedes tx-Feld inkl. `sender_ephemeral_pub` rekalkulieren können, um die Signaturkette zu verifizieren — Redaktion würde die Verifikation brechen. Erwartetes Triage-Ergebnis: `[INTENTIONAL DESIGN REQUIREMENT]` → Code-Doku (englisch) + Invariantentest, KEIN Logik-Fix. Hypothese dient der bewussten Dokumentation des Offenvektors.
- **Priorität:** LOW

## H-02-7 — Mutation-Lücken (KRITISCH laut uncovered_code.md): Negations-/Binding-Mutanten ohne Tests
- **Status Phase B:** FALSE-POSITIVE (+Regression-Guards) — Kein Code-Defekt: alle Soll-Invarianten gelten bereits auf unverändertem Code; Test `audit_02_07_identity_hkdf_and_short_hash_invariants_are_pinned` pinnt jetzt Uppercase-Prefix-Ablehnung, Did/Checksum-Tausch, HKDF-SAI-Sensitivität + Wrong-ID-Fail-Closed und Short-Hash-Tail-Ableitung und killt die überlebenden Mutanten-Klassen.
- **Vermutung:** Drei Surviving-Mutant-Cluster zeigen fehlende Soll-Verhaltens-Pinierung: (a) `validate_user_id`-**Negation** (crypto_utils.rs:817 im Mutanten-Report ≡ crypto_identity.rs:119–168): Es gibt keinen negativen Test für **manipulierte Checksums**, vertauschte did:key-Segmente bei gültiger Checksum oder Uppercase-Prefixe — Mutanten, die Checks invertieren/überspringen, surviven. (b) `build_hkdf_info` (Salt/Info, ~309 ≡ crypto_dh.rs:38–54): Kein Test pinalisiert die kanonische pk-Ordnung (Symmetrie `info(pk1,pk2)==info(pk2,pk1)`), die `recipient_id`-Sensitivität (SAI-Binding!) oder dass `decrypt_recipient_payload` mit falscher `recipient_id` FAIL-en muss — Entfernen des Bindings bliebe unentdeckt und würde Cross-SAI-Key-Reuse ermöglichen. (c) `get_short_hash_from_user_id` Index-Logik (~134 ≡ crypto_utils.rs:121–138): Fallback-/Tail-Kopier-Branches ungetestet (Peer-Tracking-Heuristik könnte still auf All-Zeros kollabieren).
- **Betroffene Invariante:** SAI-Binding der HKDF-Ableitung (`recipient_id` zwingend im info-String); kanonische Identity-Grammatik inkl. Checksummen-Integrität; deterministische Peer-Short-Hashes.
- **Zielcode:** `src/services/crypto_identity.rs` :: `validate_user_id` (~119–168); `src/services/crypto_dh.rs` :: `build_hkdf_info` (~38–54); `src/services/crypto_utils.rs` :: `get_short_hash_from_user_id` (~121–138)
- **Geplanter Fail-First-Test:** Dreiteiliger Invariantentest: (1) `assert!(!validate_user_id(tampered_checksum_id))` und `assert!(!validate_user_id(uppercase_prefix_id))`; (2) `assert_eq!(build_hkdf_info(pk_a,pk_b,id), build_hkdf_info(pk_b,pk_a,id))`, `assert_ne!(…, build_hkdf_info(pk_a,pk_b,"other:sai"))` sowie End-to-End `assert!(decrypt_recipient_payload(guard, sk, WRONG_ID).is_err())`; (3) `assert_eq!(get_short_hash_from_user_id(x), get_short_hash_from_user_id(x))` + Tail-4-Bytes-Eigenschaft gegen Referenz-Hash. Teile davon PASSen evtl. auch unpatched — der Test muss mindestens die Mutanten (a)+(b) killen, sonst ist er als Fail-First zu schärfen (insb. (2)-End-to-End und (1)-Checksumme FAILen aktuell als *fehlende* Absicherung erst durch Mutanten-Nachweis; Triage entscheidet je Einzelfall).
- **Triage-Vorabcheck:** Könnte `[INTENTIONAL DESIGN REQUIREMENT]` sein? Nein — hier geht es um Test- vs.-Code-Lücken; falls alle Asserts auf unverändertem Code PASSen, ist das Ergebnis `[FALSE POSITIVE]`/Regression-Guard (dokumentieren), nicht ein Fix. Das 3-Base58-Zeichen-Checksum (~17 bit) ist als reine Heuristik dokumentiert und kein KDF — kein Fix-Kandidat.
- **Priorität:** MEDIUM
